# lookpup(봐주개) 코드 리뷰 (2026-06-24)

이번엔 채팅 플로우가 크게 들어왔네요. 선택을 확정하면 채팅 안내 카드가 뜨고, 예약(결제)이 성공하면 채팅방이 자동으로 생기고, 새로 생긴 채팅방이 펫시터 목록에 실시간으로 반영되는 데까지요. 새 코드 위주로 보되, 11차에서 [필수]로 짚었던 결제 웹훅 버그가 고쳐졌는지부터 확인했습니다.

먼저 로그인 이야기를 짚고 갑니다. 봐주개는 로그인이 구글/카카오 OAuth 뿐이라 그동안 자동화 테스트에서 로그인 동선을 끝까지 따라가기가 어려웠는데, 이번엔 **앱 코드는 전혀 건드리지 않고** 리뷰 쪽에서만 로그인 상태를 만드는 방법을 마련했습니다(아래 E2E 결과·5번 참고). 그래서 마이프로필·정산·채팅·예약처럼 로그인이 필요한 화면까지 실제 로그인 상태로 봐줄 수 있었습니다.

| 지난 지적 | 상태 | 확인한 내용 |
| --- | --- | --- |
| [필수] 결제 웹훅 컬럼 버그 (`payment_id` → `id`) | **미해결** | `webhook/route.ts:58`이 여전히 `.eq("payment_id", paymentId)`. 아래 2-1. |

## 2. 팀 공통 — 이번 회차 [필수]

### 2-1. [필수] 결제 웹훅이 결제건을 못 찾습니다 (11차에서 이어짐)

결제가 끝나면 포트원이 웹훅을 쏘는데, 그 핸들러가 결제 행을 못 찾고 그대로 끝나 버립니다.

```ts
// reservations.ts:70 — payments 저장: 포트원 결제 ID가 PK(id)로 들어감
await db.from("payments").insert({ id: input.payment_id, ... });

// webhook/route.ts:58 — 그런데 조회는 payment_id 컬럼으로 찾음
const { data: payment } = await db
  .from("payments")
  .select("id, reservation_id")
  .eq("payment_id", paymentId)   // ← payments에는 이 컬럼이 없습니다
  .maybeSingle();

if (!payment) {
  // 못 찾으면 200으로 조용히 끝 → 결제 상태가 영영 'ready'에 머물고
  // reservation도 'paid'로 안 바뀝니다.
```

저장은 `id`에 해놓고 조회는 `payment_id`로 하니 항상 빈 결과만 돌아옵니다. 결제가 실제로 됐어도 시스템상으로는 미완으로 남는 셈이라, 서비스의 핵심 동선인 예약→결제→확정이 끊겨 버립니다. 고치는 건 한 글자(`payment_id` → `id`)지만 영향이 커서 최우선으로 봐주세요.

### 2-2. [필수] 프로덕션 빌드가 타입 에러로 멈춰 있습니다

이번엔 설치 문제가 아니라 실제 타입 에러였습니다. `npx tsc --noEmit`을 돌려 보면 다음이 잡힙니다.

```
reservations.ts(310,311,312,377,378,379): TS2352
  — Supabase 조인 결과(배열)를 단일 객체 타입으로 단언하고 있어 타입이 안 맞음
mypets/page.tsx(880,892,906): TS18047 — 'prev' 가 null 일 수 있음
```

`reservations.ts`의 여섯 줄은 전형적으로 빠지기 쉬운 함정입니다. Supabase에서 `users(...)`, `pets(...)` 같은 조인을 하면 결과가 **배열**로 추론되는데, 코드는 `as SitterRow`처럼 단일 객체로 단언하고 있어서 컴파일러가 막아섭니다(3차 때도 비슷한 게 있었죠). 가이드에 "조인 결과를 객체로 받는 정석"을 정리해 둘게요. 빌드가 막히면 배포 자체가 안 되니 이것도 [필수]로 둡니다.

### 2-3. [필수] 정산 합계가 50건에서 잘립니다 (이월)

`earnings/route.ts:35-67`이 `.limit(50)`으로 가져온 행만 JS `reduce`로 더하고 있습니다. 그래서 시터 결제가 51건을 넘으면 그 뒤로는 합계에서 빠집니다. 이런 합계는 DB에서 `sum()`으로 받아오는 게 맞습니다(가이드 참고).

### 2-4. [필수→확인] 예약 시간대 중복 (이월)

같은 시터에게 같은 시간대 예약을 두 번 넣어도 막히질 않습니다. 예약을 만들기 전에 기존 예약과 시간이 겹치는지 확인하는 쿼리가 한 번 들어가야 합니다.

## 3. 채팅 플로우 신규 코드 (영은/0sliverchoi321z)

구조를 잘 나눴습니다(안내 카드 컴포넌트, `findOrCreateRoom` 분리). 두 가지만 봐주세요.

- **[필수→제안 경계] `direct` 채팅방이 중복으로 생길 수 있습니다.** `chat.ts:38-53`의 `findOrCreateRoom`이 SELECT 해보고 없으면 INSERT 하는 구조인데, `direct` 타입엔 DB unique 제약이 없습니다(`request` 타입만 `(request_id, sitter_id)` unique). 예약 성공 직후처럼 짧은 사이에 두 번 호출되면 같은 두 사람 사이에 1:1 방이 두 개 생길 수 있어요. `(owner_id, sitter_id, room_type)` unique 인덱스를 추가하고 `upsert(onConflict)`로 바꾸면 DB가 중복을 막아 줍니다.
- **[제안] 미구독 방의 미리보기 갱신 갭** — `useChatRooms.ts:190`에서 `if (sender_id !== userIdRef.current) return;`로 자기 메시지만 미리보기를 갱신하고, 상대 메시지의 미리보기는 broadcast 채널이 맡고 있습니다. 그런데 아직 열어 보지 않아 broadcast를 구독하지 않은 방은 상대가 보낸 메시지의 미리보기가 안 바뀌는 구간이 생깁니다. 이 조건을 다시 한번 점검해 보세요(자기 메시지를 제외하는 쪽이든, 조건 자체를 손보는 쪽이든).

## 4. 그 밖에 — [제안]

- **결제 고객 정보가 더미로 하드코딩**돼 있습니다. `petsitters/[id]/book/page.tsx:701-705`에 `fullName: "테스트"`, `phoneNumber: "010-0000-0000"`, `email: "test@test.com"`이 그대로 들어갑니다. 테스트 더미가 운영으로 나가는 상태이니, 실제 로그인 사용자 정보로 채워 주세요.
- **인증 가드 부재** — `/chat`, `/myprofile/earnings`, `/petsitters/[id]/book`이 비로그인 상태에서도 화면이 렌더됩니다(데이터야 API가 막아 안 보이지만, 빈 화면은 그대로 노출됩니다). `src/middleware.ts`가 없어 서버 단 보호도 없는 상태고요. `/board/write`에서 쓴 `if (!isLoggedIn) router.replace("/auth/login")` 패턴을 적용하거나, 아예 미들웨어로 한 번에 막으면 좋겠습니다.
- **수수료율 통일** — 코드는 5%, SQL 기본값은 10%입니다. 실제 적용되는 건 코드(5%)지만 둘이 달라 혼선이 생기니 한쪽으로 맞춰 주세요.
- `/report`로 직접 들어가면 404입니다(실제 경로는 `/myprofile/report`). 공유 링크에서 생길 혼선을 줄이려면 redirect를 하나 두는 것도 방법입니다.

## 5. 로그인 / 테스트 접근

봐주개는 로그인이 OAuth 뿐이라 자동화에서 막혀 있었는데, 이번엔 리뷰 쪽 테스트 하니스에서만 동작하는 로그인을 만들어 풀었습니다(`review/e2e/auth-setup.cjs`). 동의가 필요한 구글 로그인을 흉내 내는 대신, 관리자(service-role) 권한으로 정식 세션을 발급해서 테스트 브라우저에만 그 세션을 심는 방식이라 **여러분 앱 코드엔 어떤 변경도 들어가지 않습니다.** 그래서 로그인 때문에 따로 해주실 건 지금은 없습니다.

다만 두 가지만 부탁합니다.

- 위 3번의 **인증 가드** — `/chat`·`/myprofile/earnings`·`/petsitters/[id]/book`이 비로그인 상태에서도 빈 화면으로 열립니다. 미들웨어나 페이지 가드로 막아 주세요.
- **관리자 기능을 만들 계획이라면**, 그 영역엔 화면 가드뿐 아니라 서버 쪽 권한 검사를 꼭 넣어 주세요. 다른 조에서 이번에 딱 이 부분이 문제가 됐습니다. 나중에 리뷰어 계정에 관리자 권한을 주시면 관리자 동선도 함께 검증하겠습니다.
