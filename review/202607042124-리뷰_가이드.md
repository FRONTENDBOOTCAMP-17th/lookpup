## 1. [필수/보안] 1원 결제 — `createPayment`가 클라이언트 금액을 믿지 않게

지금 구조를 보면, `payments.ts`의 `createPayment`가 `requestedAmount`라는 인자를 받아서 이걸 그대로(혹은 `??`로) 결제 금액으로 써버립니다.

```ts
// payments.ts:86
const amount = requestedAmount ?? reservation.total_price;
...
// payments.ts:91-96
if (requestedAmount && requestedAmount !== reservation.total_price) {
  await db
    .from("reservations")
    .update({ total_price: requestedAmount })
    .eq("id", reservationId);
}
```

이 `requestedAmount`가 `ChatClient.tsx:820`에서 클라이언트가 계산한 `totalAmount`를 그대로 넘겨받습니다.

```ts
// ChatClient.tsx:820
const payResult = await createPayment(reservationId, "CARD", totalAmount);
```

브라우저 개발자도구에서 이 `totalAmount`를 1로 바꿔서 호출하면, 서버는 그 값을 그대로 결제 금액으로 저장하는 것도 모자라 예약의 `total_price`까지 1로 덮어씁니다. 웹훅에서 포트원 API를 재조회해 금액을 대조하는 로직이 있긴 하지만, 그건 "이미 1로 저장된 값"과 "포트원에서 1원 결제된 값"을 비교하는 거라 통과해버립니다. 즉 지금 검증은 "결제 도중 금액이 바뀌었는가"만 잡지, "애초에 얼마를 결제해야 하는가"는 서버가 정하지 않고 있습니다.

해결 방향은 간단합니다. `requestedAmount`라는 매개변수 자체를 없애고, 서버가 예약 데이터를 기준으로 결제 금액을 다시 계산하게 만들면 됩니다.

```ts
// payments.ts — createPayment 시그니처에서 requestedAmount 제거
export async function createPayment(reservationId: string, payMethod: string) {
  const db = createServiceClient();

  const { data: reservation } = await db
    .from("reservations")
    .select("id, owner_id, sitter_id, total_price, status")
    .eq("id", reservationId)
    .single();

  if (!reservation) {
    return { error: { code: "NOT_FOUND", message: "예약을 찾을 수 없습니다." } };
  }

  // 서버가 신뢰하는 값은 오직 reservation.total_price 뿐입니다.
  const amount = reservation.total_price;
  const platformFee = Math.floor(amount * FEE_RATE);
  const settleAmount = amount - platformFee;
  const paymentId = `pay_${reservationId.replace(/-/g, "")}_${Date.now()}`;

  // total_price를 덮어쓰는 코드(:91-96)는 통째로 삭제합니다.

  const { error } = await db.from("payments").insert({
    reservation_id: reservationId,
    payment_id: paymentId,
    owner_id: reservation.owner_id,
    sitter_id: reservation.sitter_id,
    amount,
    pay_method: payMethod,
    fee_rate: FEE_RATE,
    settle_amount: settleAmount,
    status: "ready",
  });

  if (error) return { error: { code: "INTERNAL_ERROR", message: error.message } };
  return { data: { paymentId, amount } };
}
```

그리고 `ChatClient.tsx:820`의 호출부에서는 세 번째 인자만 빼주세요.

```ts
// ChatClient.tsx:820
const payResult = await createPayment(reservationId, "CARD");
```

화면에 결제 금액을 미리 보여주는 건 그대로 `totalAmount`(클라 계산값)로 해도 됩니다. 사용자 경험에 문제 될 게 없습니다. 다만 실제로 결제·저장되는 금액만큼은 서버가 DB에서 읽은 **`reservation.total_price`**를 쓰도록 만들면, 클라이언트가 뭘 보내든 서버가 그 값을 무시하니 1원 결제 자체가 성립하지 않습니다. 만약 추가금(청소비·연장 등)처럼 예약 생성 이후 금액이 바뀌는 케이스가 있다면, 그 값도 서버 쪽 테이블(예: `extra_charges`)에서 조회해 더하는 식으로 처리하면 됩니다. 클라이언트가 숫자를 "얼마"라고 불러주는 경로 자체를 없애는 게 핵심입니다.

## 2. [필수/보안] 자기예약 차단

`createReservation`(`reservations.ts:35-130`)은 서비스가 실제로 그 시터 소유인지는 확인하는데(87행 `service.sitter_id !== input.sitter_id`), 정작 예약을 요청하는 사람이 그 시터 본인인지는 확인하지 않습니다. 시터가 자기 자신에게 예약을 넣어서 후기·정산 수치를 조작하는 경로가 열려 있는 셈입니다.

서비스 존재 확인 로직 바로 다음(94행 이후, `reservations` insert 이전)에 이 한 단계만 넣어두세요.

```ts
// reservations.ts — createReservation, service 검증 다음 줄
if (service.sitter_id === user.id) {
  return {
    error: { code: "FORBIDDEN", message: "본인에게는 예약할 수 없습니다." },
  };
}
```

`service.sitter_id`는 이미 위에서 조회해둔 값이라 추가 쿼리 없이 바로 비교할 수 있습니다. UI에서 버튼을 숨기는 것과 별개로, 서버에서 막아둬야 API를 직접 호출하는 우회까지 잡힙니다.

## 3. [필수/보안] 공개 RPC의 개인정보 축소

`get_petsitters_filtered`는 지도/목록에서 익명 사용자도 호출할 수 있는 RPC인데, 실제로 호출해보면 이렇게 응답합니다.

```json
{
  "id": "...",
  "user_id": "a1000000-...",
  "full_name": "정우성",
  "available_area": "광주광역시 북구 두암동",
  "display_area": "북구 두암동",
  "latitude": 35.19, "longitude": 126.915,
  ...
}
```

`display_area`(구·동 이름만)와 fuzz 처리된 좌표는 이미 잘 만들어뒀습니다. 그런데 그 옆에 실명(`full_name`)·인증 계정 UUID(`user_id`)·전체 상세주소(`available_area`)가 그대로 같이 나가고 있습니다. 지도에 마커를 찍고 카드에 이름을 보여주는 데는 `display_area`와 fuzz 좌표만으로 충분하니, 이 세 필드만 반환에서 빼주세요.

```sql
-- get_petsitters_filtered 함수 정의에서 SELECT 절 수정
-- 기존: select id, user_id, full_name, available_area, display_area, latitude, longitude, base_price, rating, service_types
-- 변경:
select
  id,
  display_area,        -- 구·동 단위만
  latitude,            -- 이미 fuzz된 좌표
  longitude,
  base_price,
  rating,
  service_types
from ...
```

목록 카드에서 지금 `full_name`을 쓰는 곳(예: 펫시터 카드 컴포넌트)이 있다면, 그 화면에서 이름 대신 "OO동 펫시터" 같은 표현으로 바꾸거나, 상세 페이지 진입 시(로그인/권한이 확인되는 경로) 별도로 이름을 조회하도록 옮겨두세요. `database.types.ts:1096-1108`의 `Returns` 타입도 RPC를 고친 뒤 `supabase gen types`로 다시 생성해서 `full_name`·`user_id`·`available_area`가 타입에서도 함께 사라지는지 확인해주세요.

## 4. [제안] Supabase 클라이언트 싱글턴으로 통합

`src/lib/supabase.ts:7`과 `src/utils/supabase/client.ts:5`가 각각 `createClient`/`createBrowserClient`로 브라우저용 클라이언트를 따로 만들고 있어서, 콘솔에 "Multiple GoTrueClient instances" 경고가 뜨고 있습니다. 세션 저장소를 두 클라이언트가 각자 관리하다 보면 로그인 상태가 어긋나는 사고로 이어질 수 있으니, 브라우저 쪽은 한 곳(`utils/supabase/client.ts`)만 남기고 `src/lib/supabase.ts`를 참조하는 곳들을 그쪽으로 옮기는 걸 권합니다.

```ts
// src/lib/supabase.ts를 쓰던 곳들
import { createClient } from "@/utils/supabase/client";
const supabase = createClient();
```
