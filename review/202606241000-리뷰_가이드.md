## 1. 결제 웹훅이 결제건을 찾도록 (`webhook/route.ts:58`)

`payments`는 포트원 결제 ID를 PK인 `id`에 저장하고 있는데(`reservations.ts:70`의 `id: input.payment_id`를 보면 그렇죠), 그렇다면 조회할 때도 똑같이 `id`로 찾아야 맞습니다.

```ts
// webhook/route.ts:58
const { data: payment } = await db
  .from("payments")
  .select("id, reservation_id")
  .eq("id", paymentId)        // ← payment_id 에서 id 로
  .maybeSingle();
```

고친 뒤에는 흐름이 끝까지 이어지는지 한 번 확인해 보세요. 결제를 실제로 한 번 태웠을 때 `payments.status`가 `ready`에서 `paid`로 넘어가고 연결된 `reservations`까지 `paid`가 되면 제대로 도는 겁니다. 지금은 웹훅이 결제건을 못 찾은 채 200으로 끝나버려서 상태가 영영 `ready`에 멈춰 있는 상황입니다.

> 같은 실수가 다른 곳에도 숨어 있을 수 있으니, `payment_id`로 `payments`를 조회하는 코드가 더 없는지 한 번 검색해 보면 좋겠습니다.

## 2. 빌드 막는 타입 에러 풀기

### 2-1. Supabase 조인 결과는 배열로 온다 (`reservations.ts:310~`)

`select("..., users(full_name), pets(...)")`처럼 조인하면 Supabase가 관계 데이터를 **배열**로 돌려주는데, 1:1 관계여도 타입상으로는 배열로 추론하다 보니, 이걸 단일 객체로 보고 `as SitterRow` 단언하면 컴파일러가 막아서는 겁니다.

푸는 길은 두 가지입니다.

**방법 A — 쿼리에서 단일 관계를 명시 (권장)**: Supabase는 `!inner`나 외래키 힌트로 단일 관계를 표현할 수 있는데, 무엇보다 받은 뒤에 배열을 한 번 펴 주면 됩니다.

```ts
const { data } = await db
  .from("reservations")
  .select("..., sitters(available_area, rating, users(full_name))")
  .eq("id", id)
  .single();

// users 가 배열로 오므로 첫 요소를 꺼내 씀
const sitter = data.sitters;
const fullName = sitter?.users?.[0]?.full_name ?? null;
```

**방법 B — 타입을 실제 형태(배열)에 맞추기**: `SitterRow`의 `users`를 `{ full_name: string }[]`로 정의하면 단언 없이도 통과합니다. 타입을 데이터의 실제 모양에 맞춰 주는 방식이죠.

`as`로 억지로 우회하는 방법(`as unknown as SitterRow`)도 있긴 한데, 이건 컴파일만 통과시킬 뿐 런타임에 `users[0]`을 `users`로 잘못 읽는 버그를 그대로 덮어버릴 수 있어 권하지 않습니다. 데이터가 배열로 온다는 사실 자체에 코드를 맞추는 편이 안전합니다.

### 2-2. `prev` null 체크 (`mypets/page.tsx:880,892,906`)

`setState(prev => ...)`에서 컴파일러는 `prev`가 null일 수도 있다고 봅니다. 초기값을 null이 아니게 잡아두거나, 콜백 안에서 가드를 한 줄 넣어 주면 됩니다.

```ts
setPets(prev => {
  if (!prev) return prev;       // 또는 초기 상태를 [] 로
  return prev.map(...);
});
```

## 3. 정산 합계를 DB에서 (`earnings/route.ts:35-67`)

`.limit(50)`으로 끊은 다음 JS에서 합산하면 50건까지만 맞고 그 위로는 누락됩니다. 합산은 DB가 전부 떠안게 넘기는 게 좋습니다.

```ts
// 현재 (50건까지만)
const { data } = await db.from("payments").select("settle_amount").eq("sitter_id", id).limit(50);
const total = data.reduce((s, p) => s + p.settle_amount, 0);

// 개선 — DB 집계
const { data } = await db
  .from("payments")
  .select("settle_amount.sum()")
  .eq("sitter_id", id)
  .eq("status", "paid")
  .single();
const total = data?.sum ?? 0;
```

혹시 이 집계 문법이 환경에서 안 먹으면, 합계용 RPC를 하나 만들어 써도 됩니다.

```sql
create or replace function sitter_earning_total(p_sitter_id uuid)
returns bigint language sql stable as $$
  select coalesce(sum(settle_amount), 0) from payments
  where sitter_id = p_sitter_id and status = 'paid';
$$;
```

## 4. 예약 시간대 중복 막기

예약을 만들기 전에, 같은 시터에게 시간이 겹치는 예약이 이미 있는지부터 확인하는 게 핵심입니다.

```ts
const { data: overlap } = await db
  .from("reservations")
  .select("id")
  .eq("sitter_id", sitterId)
  .neq("status", "cancelled")
  .lt("start_datetime", newEnd)     // 기존 시작 < 새 끝
  .gt("end_datetime", newStart)     // 기존 끝   > 새 시작
  .limit(1);

if (overlap?.length) {
  return { error: "해당 시간대에 이미 예약이 있습니다." };
}
```

겹침 판정은 "기존.시작 < 새.끝 그리고 기존.끝 > 새.시작"이 성립하면 두 예약이 겹치는 것으로 봅니다. 더 단단하게 가고 싶다면 Postgres `tstzrange`와 exclusion 제약을 걸어 DB가 직접 막게 할 수도 있습니다.

## 5. 채팅방 중복 막기 (`chat.ts:38-53`)

```sql
-- direct 1:1 방은 두 사람당 하나만
create unique index uniq_direct_room
  on chat_rooms (owner_id, sitter_id, room_type)
  where room_type = 'direct';
```

```ts
// SELECT→INSERT 대신 upsert 로 경합 제거
const { data } = await db
  .from("chat_rooms")
  .upsert({ owner_id, sitter_id, room_type: "direct" },
          { onConflict: "owner_id,sitter_id,room_type" })
  .select("id")
  .single();
```
