## 2. `[필수]` 빌드가 여전히 타입 체크에서 실패합니다 (실측)

`npm run build` 결과 — 컴파일은 되지만 타입 체크에서 멈춥니다. `npx tsc --noEmit` 으로도 같은 에러가 잡힙니다.

2차에 짚었던 한 곳이 그대로 남아 있고(MapMarker `id`), **이번 새 코드에서 4곳이 더 늘었습니다.**

```
src/app/petsitters/[id]/page.tsx(352,33): TS2741  Property 'id' is missing ... MapMarker  ← 2차 지적, 미해결
src/app/actions/applications.ts(107,22): TS2352   배열 → 객체 캐스팅 불가
src/app/actions/payments.ts(82,18):       TS2352   배열 → 객체 캐스팅 불가
src/app/actions/payments.ts(109,23):      TS2352   배열 → 객체 캐스팅 불가
src/app/api/sitters/[id]/route.ts(34,40): TS2352   배열 → 객체 캐스팅 불가
```

빌드를 막는 에러이니 **이번 회차에서 꼭 닫아야 합니다.** 두 가지로 나눠 설명할게요.

### 2-1. MapMarker `id` (2차 그대로) — `src/app/petsitters/[id]/page.tsx:352`

```tsx
markers={[{ lat: PETSITTER.lat, lng: PETSITTER.lng }]}   // id 없음
```

`KakaoMap.tsx`의 `MapMarker` 인터페이스가 `id: number` 를 **필수**로 받습니다(12~17줄). `id` 하나만 넣어주면 끝입니다.

```tsx
markers={[{ id: PETSITTER.id ?? 0, lat: PETSITTER.lat, lng: PETSITTER.lng }]}
```

### 2-2. Supabase 조인 결과를 객체로 캐스팅(신규 4곳)

`applications.ts`, `payments.ts`, `api/sitters/[id]/route.ts` 에서 공통으로 이런 모양입니다.

```ts
const { data: application } = await db
  .from("applications")
  .select(`id, ..., requests!inner(id, owner_id, ...)`)
  .single();

const requestRow = application.requests as { id: string; owner_id: string; ... };  // ← 여기서 막힘
```

원인: supabase-js의 타입 추론은 `requests!inner(...)` 조인 결과를 **배열(`{...}[]`)** 로 봅니다. 그걸 단일 객체(`{...}`)로 `as` 단언하려니 "겹치는 부분이 없다"며 막는 겁니다(런타임에선 `!inner` 1:1이라 객체로 오지만, TS는 그걸 모릅니다).

해결 가이드 문서에 정석/임시 두 방법을 적어뒀습니다. 정석은 **DB 타입 제너레이트(`supabase gen types`)** 라 `as` 자체가 사라지는 방향을, 임시로는 `as unknown as {...}` 한 단계 우회를 권합니다.

  ```tsx
  const handleDelete = () => {
    setShowModal(false);
    setDone(true);          // 화면만 "완료"로 바뀜
  };
  ```
  화면은 "탈퇴 완료"로 넘어가지만 **계정은 그대로 살아 있고, 세션도 안 끊깁니다.** 마침 gyuhwa가 `actions/users.ts` 에 `deleteUser()` 서버 액션을 이미 만들어뒀습니다. 두 사람 코드를 이어붙이면 됩니다.
  ```tsx
  import { deleteUser } from "@/app/actions/users";
  import { createClient } from "@/utils/supabase/client";

  const handleDelete = async () => {
    const res = await deleteUser();
    if (res.error) { alert(res.error.message); return; }
    await createClient().auth.signOut();   // 세션도 끊기
    setShowModal(false);
    setDone(true);
  };
  ```

## 5. 보안 — RLS 실측 (anon / service 키 직접 호출)

루트 `lookpup/.env.local` 의 anon·service 키로 Supabase REST를 직접 호출했습니다.

| 테이블 | service(실제 행수) | anon 읽기 | anon 쓰기 |
| ----- | ----------------- | -------- | -------- |
| `users` | 3행 | `200 []` (0행 노출) | — |
| `sitters` | **1행** | `200 []` (0행 노출) | — |
| `pets` | 0행 | `200 []` | **`401` RLS 위반(차단)** |
| `services`·`reservations`·`payments`·`applications`·`requests`·`reviews`·`notifications` | 0행 | `200 []` | — |

해석:
- **새 테이블(`sitters`·`services`·`reservations`·`payments`·`applications`·`requests`)이 생겼습니다.** 2차엔 "테이블 미생성"이었는데 이번에 만들어졌습니다.
- **anon으로 민감 데이터가 새지 않습니다.** `sitters` 는 실제 1행이 있는데 anon에는 `[]`(0행)으로 막혔고, `users` 도 3행 중 0행만 보입니다. `pets` 쓰기는 `401 RLS 위반` 으로 명확히 차단됩니다. → **RLS가 켜져 있고 잘 동작합니다. 2차 대비 분명한 진전이라 칭찬합니다.**

다만 한 가지 **질문 겸 설계 확인**이 있습니다.
- `[제안]` **공개되어야 할 데이터까지 anon에 0행으로 막혀 있습니다.** "펫시터 찾기(지도+목록)"는 비로그인 유저도 봐야 할 텐데, `sitters` 가 anon에 `[]` 라 클라이언트에서 직접 조회하면 빈 목록이 됩니다. 지금은 `/api/sitters`(service client)로 우회하니 동작은 하지만, 이건 "service role 키로 RLS를 통째로 우회"하는 방식이라 **모든 공개 조회가 서버 라우트를 거쳐야** 합니다. 의도한 설계라면 괜찮습니다(서버 경유 = anon 키로는 아무것도 못 읽음, 보안엔 더 안전). 다만 "활성 시터는 누구나 볼 수 있다" 같은 **SELECT 정책을 명시적으로 열어두는 방향**도 있으니, 어느 쪽으로 갈지 팀에서 한 번 정해두면 좋겠습니다.
