## 2. 정산 합계를 DB SUM으로 — `api/earnings/route.ts`

```ts
// 변경 전: limit(50) 후 JS reduce → 50건 넘는 시터는 합계가 틀림
// 변경 후: RPC로 전체 합계를 정확히 (limit 없이)
```

```sql
create or replace function sitter_earnings(p_sitter_id uuid)
returns table(period text, total bigint) language sql security definer as $$
  select 'total', coalesce(sum(settle_amount),0)::bigint
    from payments where sitter_id = p_sitter_id and status = 'paid'
  union all
  select 'this_month', coalesce(sum(settle_amount),0)::bigint
    from payments where sitter_id = p_sitter_id and status='paid'
      and paid_at >= date_trunc('month', now());
$$;
```

목록(최근 거래 50건)은 지금처럼 limit으로 보여 주더라도, **합계만큼은 별도 SUM 쿼리나 RPC로** 떼어 내는 게 좋습니다. 화면에 뿌릴 목록과 정확히 더해야 하는 합계는 애초에 다른 쿼리라고 보면 됩니다.

## 3. 예약 시간대 중복 막기 — `actions/reservations.ts`

INSERT 하기 전에 겹치는 예약이 있는지 코드에서 확인하는 방법도 있고, 아예 DB 제약으로 막는 방법도 있는데요, 둘 중에서는 DB 제약이 가장 확실합니다.

```sql
create extension if not exists btree_gist;
alter table reservations
  add constraint no_overlap_per_sitter
  exclude using gist (
    sitter_id with =,
    tstzrange(start_at, end_at) with &&
  ) where (status in ('accepted','paid','in_progress'));
```

이렇게 해 두면 같은 시터의 시간대가 겹치는 예약은 DB가 알아서 거절하니, 앱 쪽에서 검사를 깜빡해도 막힙니다. 컬럼명(start_at/end_at)은 실제 스키마에 맞춰 바꿔 주세요.

## 4. 지도·목록을 DB에서 페이지네이션 — `petsitters/page.tsx`, `api/sitters/route.ts`

지금은 RPC가 전체를 다 반환하고 클라이언트에서 slice 하는 구조인데요, LIMIT/OFFSET(또는 cursor)과 반경 필터를 RPC 안에서 처리하도록 바꿔 주세요.

```sql
-- RPC가 반경 + 정렬 + 페이지네이션까지 책임지게
create or replace function search_sitters_within(
  p_lat float, p_lng float, p_radius_km float, p_limit int, p_offset int
) returns setof sitters language sql stable as $$
  select * from sitters
  where status = 'approved'
    and earth_distance(ll_to_earth(latitude, longitude), ll_to_earth(p_lat, p_lng)) <= p_radius_km * 1000
  order by earth_distance(ll_to_earth(latitude, longitude), ll_to_earth(p_lat, p_lng))
  limit p_limit offset p_offset;
$$;
-- earthdistance 확장: create extension if not exists cube; create extension if not exists earthdistance;
```

지금은 거리 계산이 클라이언트와 RPC 두 곳에 나뉘어 있는데, 이걸 RPC 한 곳으로 모아 두면 결과도 어긋날 일이 없습니다. `reviewCount`는 실제 리뷰 수를 조인해서 채워 주시고, 그게 어렵다면 차라리 "리뷰순 정렬" 옵션을 빼는 편이 정직합니다.
