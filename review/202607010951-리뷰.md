## 2. [필수·중대] 결제 금액이 서버에서 검증되지 않습니다

이건 실제로 재현했습니다. `/payment?amount=1&fee=0.05`로 접속하면 화면에 "예약 금액 1원 / 총 결제 금액 1원 / 결제하기 1원"이 그대로 뜹니다(캡처 `review/images/2026-07-01/lookpup-payment-amount1.png`). 결제 금액을 URL로 조작할 수 있는 상태가 지난 회차에서 달라지지 않았습니다.

경로를 코드로 따라가 보면 세 군데 모두 금액을 클라이언트 값 그대로 믿습니다.

- **화면**: `payment/page.tsx:57` `Number(searchParams.get("amount"))`를 검증 없이 PortOne `requestPayment.totalAmount`(83-94)로 넘김.
- **DB 기록**: `ChatClient.tsx:517`이 `createPayment(reservationId, "CARD", data.amount)`를 부르고, `actions/payments.ts:86`이 `const amount = requestedAmount ?? reservation.total_price` — 즉 예약의 `total_price`가 아니라 **결제요청 카드 메시지에 발신자가 채운 amount**를 그대로 `payments.amount`로 저장합니다. `total_price`와 대조하는 코드가 없습니다.
- **웹훅**: `api/portone/webhook/route.ts`의 서명 검증(5-24)은 정상인데, `Transaction.Paid`(71) 처리에서 PortOne이 실제 승인한 금액을 조회해 대조하지 않고 무조건 `status:"paid"`로 마킹합니다.

결제 확정은 서버가 진실이어야 합니다. 세 곳을 이렇게 바꾸면 됩니다. (1) `createPayment`에서 `requestedAmount`를 믿지 말고 1차 결제는 `reservation.total_price`로 강제하고, (2) 웹훅 `Transaction.Paid`에서 PortOne `GET /payments/{id}`로 실제 승인액을 조회해 일치할 때만 `paid`로 처리하며, (3) `/payment` 페이지는 URL amount를 화면 표시용으로만 쓰고 실제 요청 금액은 서버가 돌려준 값을 쓰게 합니다. 코드는 가이드에 담았습니다.

## 3. [필수] 프로덕션 빌드가 타입 에러로 안 됩니다

`npm run build`가 "✓ Compiled successfully" 다음에 **"Failed to type check"로 종료**됩니다. `tsc --noEmit`으로 8건이 잡힙니다. 모두 Supabase 생성 타입과 안 맞는 문제입니다.

- `admin.ts:205`, `pets.ts:194`, `services.ts:125` — `.update()`에 `Record<string, ...>`/`Partial`을 그대로 넘겨 생성 타입과 충돌 (gyuhwa)
- `sitters.ts:154, 200, 309` — 같은 패턴 (박규나)
- `admin/page.tsx:13`, `admin/state/page.tsx:6` — 조인한 `sitter.users`에 `id`가 select에 없어 `UserInfo` 타입 불일치 (gyuhwa)

`next.config`에 `ignoreBuildErrors`가 없어서(이건 옳은 설정입니다) 빌드가 진짜로 막힙니다. dev 서버로는 잘 떠서 E2E는 됐지만, 이는 **지금 develop/dev에 빌드가 안 되는 코드가 머지돼 있다**는 뜻이라, 배포를 하려면 이게 먼저 풀려야 합니다. 수정은 update 페이로드 타입을 좁히고(`satisfies TablesUpdate<'...'>`) admin 조인 select에 `id`를 추가하면 되고, 여기에 더해 `supabase gen types`에 RPC를 포함해 다시 뽑으면 곳곳의 `as any` 캐스팅까지 상당수가 한 번에 정리됩니다(가이드 참고).

## 4. 보안 실증

anon 키로 직접 읽어 본 결과, RLS는 대체로 잘 잠겨 있습니다. `notifications`·`users`·`payments`·`reservations`·`sitters`·`messages`·`chat_rooms`·`applications`·`reports`·`pets` 모두 anon read 0행이었습니다. **15차의 notifications RLS 지적은 해결됐습니다.** gyuhwa님 RLS 작업 좋았습니다.

두 군데가 남았습니다.

### [필수] 공개 펫시터 RPC가 anon에 실명 + user_id + 좌표를 줍니다

`get_petsitters_filtered`(펫시터 목록이 쓰는 RPC)를 anon 키로 직접 부르면 HTTP 200으로 29행이 내려오는데, 여기에 `user_id`(auth UUID)·`full_name`(실명)·`latitude`/`longitude`가 들어 있습니다. 좌표는 소수점 2자리로 반올림돼(동네 수준 ~1km) 건물 단위까지는 아니지만, **로그인도 안 한 사람에게 실명과 auth id를 주는 건 과합니다.** 화면(`lookpup-petsitters.png`)은 실제로 `display_area`("북구 두암동")만 쓰고 있습니다. RPC 반환에서 `user_id`·`full_name`·정확 좌표를 빼고 지도엔 표시명과 대략 좌표만 주면 되고, 세부 정보는 상세로 들어온 인증 사용자에게만 열어 주면 됩니다.

### [제안] `reviews`만 anon에 노출됩니다

`reviews`가 anon으로 9행 읽히는데, `owner_id`·`sitter_id`(둘 다 UUID)에 평점·본문까지 포함됩니다. 후기를 공개하는 것 자체는 맞지만, UUID로 "누가 누구를 리뷰했는지" 매핑이 그대로 노출됩니다. 반환에서 `owner_id`를 빼거나 표시명만 주면 됩니다.

### [제안] `/api/sitters`는 죽은 라우트입니다

`api/sitters/route.ts`가 존재하지 않는 RPC `search_sitters_within`을 부르는 탓에 모든 요청이 500으로 떨어집니다(PGRST202 실측). 페이지는 `get_petsitters_filtered`를 쓰니 이 라우트는 **미사용인데 상시 500**인 셈입니다. 게다가 service client(RLS 우회)에 무인증이라, 나중에 그 RPC가 생기면 곧바로 PII 라우트가 되어 버립니다. 삭제하거나 `get_petsitters_filtered` 기준으로 통일하세요.

- **[필수] 빌드가 안 되는 상태로 통합 브랜치에 머지되고 있습니다.** 타입 에러 8건이 dev HEAD에 살아 있다는 건, "내 층은 빌드 통과로만 머지" 규칙과 CI(`tsc --noEmit`)가 아직 없다는 뜻입니다. GitHub Actions에 `tsc` + `eslint` 게이트를 붙이면 층별 타입 에러가 통합 브랜치로 새는 걸 막을 수 있고, 마감 전에 이거 하나 붙여 두면 남은 나흘이 훨씬 안전해집니다.

- `no-explicit-any`가 73건인데, 특히 Supabase RPC 캐스팅(`as any`, `as unknown as`)이 반복됩니다. 생성 타입에 RPC 시그니처가 없어서 생긴 우회입니다. `supabase gen types`에 RPC를 포함해 다시 뽑으면 캐스팅과 빌드 에러가 상당수 함께 사라집니다.
