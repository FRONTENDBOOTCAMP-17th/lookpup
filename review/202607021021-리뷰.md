# lookpup(봐주개) 17차 코드 리뷰 (2026-07-02)

마감(7/8)까지 나흘 남았네요. 어제(16차) 오전 이후 dev에 커밋이 74개나 쌓여서, 이번 회차 delta가 지금까지 중 제일 컸습니다. 절반 이상이 리팩토링이었습니다 — 홈·소개·펫시터 찾기 hook/utils 분리, 펫 등록·시터 등록 계층 분리, myprofile·board 서버 패칭, Auth 정리까지요. 그 위에 포트원 웹훅 상태 동기화, 추가금 결제 요청 카드, 채팅 실시간 보강이 얹혔습니다. 리팩토링이 이번 핵심인 만큼 "분리가 정말 응집도를 높였는가"까지 함께 봤습니다.

순서는 ① 지난 반영 현황 → ② E2E 결과 → ③ 1원 결제 추적 → ④ 리팩토링 평가 → ⑤ 조원별 → ⑥ 팀 공통 순입니다.

## 2. E2E 결과 (2026-07-02)

dev 서버(포트 3300)로 사용자 여정을 돌렸습니다. 로그인은 기존 테스트 전용 세션(service-role로 발급했고 앱 코드는 손대지 않았습니다)을 그대로 재사용했고요. 신규 엔드포인트(정산 수익 차트·예약 내역·시터 프로필 편집·about/terms/privacy)는 하나도 빠짐없이 시나리오에 넣었습니다. 26개 중 25개 통과, 1개 실패였습니다.

| 라우트 | 상태 | 메모 |
| --- | --- | --- |
| `/`, `/petsitters`, `/petsitters/[id]`, `/board`, `/chat` | 200 | 인증 후 튕김 없음 |
| `/myprofile/earnings`(수익 차트) | 200 | recharts 정산 화면 정상 렌더 |

| **`/terms`** | **HTTP 500** | 서버 컴포넌트가 함수 prop을 클라 컴포넌트에 전달 — 아래 |
| `/report` | 404 | 라우트 존재 여부 확인 필요 |

![수익 관리(정산 차트)](../images/2026-07-02/lookpup-A5-earnings-chart.png)

정산 수익 화면은 카드·월별 차트·거래 내역까지 깔끔하게 잘 나왔습니다(테스트 계정은 수익이 0이라 차트가 비어 보이는 것뿐이고, 화면 자체는 정상입니다).

### [필수] `/terms` 500 — 함수 prop을 Client Component에 직접 전달

`/about`·`/privacy`는 200인데 유독 `/terms`만 500이 나더군요. 서버 로그에 원인이 그대로 찍혀 있습니다.

```
Error: Functions cannot be passed directly to Client Components unless you
explicitly expose it by marking it with "use server".
  <... renderItemText={function renderItemText}>
```

`LegalPage`는 `"use client"` 컴포넌트인데, `terms/page.tsx`(서버 컴포넌트)가 `renderItemText`라는 **함수를 prop으로 넘기고 있습니다**. React는 서버→클라 경계로 함수를 직렬화할 수 없어서 렌더가 통째로 실패하는 거고요. about·privacy는 이 함수를 안 넘기니 멀쩡했던 거였습니다. 이용약관은 법적으로도 꼭 열려 있어야 할 페이지라, 마감 전 [필수]로 봐야 합니다. 해결은 가이드에 코드로 적어 뒀습니다.

부수적으로, 콘솔에 **"Multiple GoTrueClient instances"** 경고가 반복해서 뜹니다(`src/lib/supabase.ts:7`, `src/utils/supabase/client.ts:5`). Supabase 클라이언트 싱글턴이 두 갈래로 만들어지고 있다는 신호라, 하나로 모아 주는 걸 권합니다(`[제안]`).

## 3. 1원 결제 추적

방어가 한 겹 늘어난 건 분명한 진전입니다. `verifyAndConfirmPayment`(`payments.ts:244-263`)와 웹훅(`api/portone/webhook/route.ts:71-105`)이 포트원 API를 재조회해서 `paidAmount !== payment.amount`면 거절하고, 웹훅에선 HMAC 서명 검증까지 합니다. 덕분에 "체크아웃 화면에서 금액을 조작"하는 류는 막힙니다.

문제는 결제의 실제 주경로인 `createPayment(reservationId, payMethod, requestedAmount?)`가 **클라가 준 `requestedAmount`를 그대로 믿어 버린다**는 점입니다.

```ts
// payments.ts:86, 91-96
const amount = requestedAmount ?? reservation.total_price;
// ... reservation.total_price 까지 requestedAmount 로 덮어씀
```

`ChatClient.tsx:556`이 `createPayment(reservationId, "CARD", totalAmount)`로 부르는데, 이 `totalAmount`가 클라에서 계산한 값입니다. 그러니 예약 owner가 `createPayment(myReservationId, "CARD", 1)`로 호출하면, 서버가 `payment.amount = 1`은 물론 `reservation.total_price`까지 1로 덮어 저장하고, 포트원 1원 결제 → 웹훅에서 `paidAmount(1) === payment.amount(1)`이 딱 맞아떨어져 결제완료로 확정돼 버립니다. 금액 대조가 "저장된 값끼리" 이뤄지다 보니, 처음부터 낮게 저장하면 검증을 그냥 통과하는 구조인 거죠.

핵심은 **결제 요청 금액을 예약 실제가(서비스 가격 + 승인된 추가금)로 서버가 다시 계산**하게 만드는 것입니다. `createExtraPayment`엔 이미 1,000~500,000 범위 검증이 있는데, 정작 `createPayment`엔 그 관문이 없습니다. 해결은 가이드에 적어 뒀습니다.

## 4. 리팩토링 평가 (응집도/결합도)

이번 delta의 방향은 좋습니다. 페이지에 뭉쳐 있던 로직을 hook/컴포넌트로 갈라내면서 데이터와 뷰 사이에 경계가 생겼거든요.

- **잘된 분리**: `src/hooks/petsitters/`(지역 검색·위치·시터 선택·동의 조회/저장), `src/hooks/chat/`, `src/hooks/sitter-register/`·`pet-register/`, `src/components/petsitters/`의 Step·Panel·Tab 분해가 특히 좋았습니다. TanStack Query hook을 따로 뺀 덕에 캐시·로딩 상태의 응집도 올라갔고요.
- **아쉬운 신호**: 세 가지가 눈에 띕니다. 우선 `usePetsitterLocation.ts:110`에서 effect 안에서 동기 setState(`requestLocationSilently()`)를 호출하는 바람에 렌더가 연쇄됩니다(lint에서도 `set-state-in-effect`로 잡힙니다). 채팅은 아직도 broadcast + postgres_changes **이중 구독**을 그대로 두고 있는데, 중복 제거로 버그야 없어졌지만 구독이 두 배라 realtime 비용이 괜히 큽니다 — 응집 관점에선 한 소스로 합치는 게 맞습니다. 마지막으로 `api/bank-account` 라우트가 타입 없는 테이블(`bank_accounts`)을 다루느라 `never` 캐스팅을 남발하는데, 서버 패칭 리팩토링이 타입 안전성을 깎아 먹은 형태라 이대로 두면 빌드가 계속 깨집니다.

## 6. 팀 공통

- **프로덕션 빌드가 지금 실패 상태입니다(tsc 16건).** dev로는 뜨지만 배포가 막혀 있으니, 마감 전에 꼭 초록불로 되돌려 주세요. `bank_accounts` 타입 생성(6건) → `.update()` 타입 정리(8건) → admin 조인 `id` 포함(2건) 순으로 가면 빠릅니다.
- **결제는 서버가 금액의 기준이 돼야 합니다.** 웹훅에 대조를 넣은 건 좋았는데, "저장된 값끼리" 비교하면 처음부터 낮게 저장된 경우는 못 잡습니다. `createPayment`에서 예약 실제가로 다시 계산하는 지점 하나만 넣으면 방어가 완성됩니다.
- **공개 RPC의 PII**: `get_petsitters_filtered`에서 `full_name`·`user_id`·`available_area`(전체주소)를 빼면 됩니다. 지도용은 `display_area` + fuzz 좌표만으로 충분하고요. 좌표는 이미 완화해 뒀으니 나머지 세 필드만 정리하면 됩니다.
- 리팩토링 방향 자체는 좋습니다. 다만 채팅 이중 구독처럼 "두 갈래로 늘어난" 것들(구독·supabase 클라이언트)을 하나로 모으는 정리를 마감 전에 한 번 해 두면 응집도가 한층 더 올라갑니다.

우선순위는 빌드 복구 → `/terms` 500 → 1원 결제(`createPayment`) → 자기예약 차단 → RPC PII 순으로 잡으면 됩니다. 해결 코드는 가이드에 담아 뒀습니다. 화이팅입니다.
