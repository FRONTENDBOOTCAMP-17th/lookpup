# lookpup(봐주개) 코드 리뷰 — 2026-06-23

오늘은 API가 쓰는 데이터베이스 테이블(ERD)을 정리하면서, 그 위에서 느려질 만한 쿼리와 정합성 문제를 위주로 봤습니다. 마침 정산(earnings)·결제 쪽 코드가 새로 올라와 있어서, 결제에서 예약을 거쳐 정산으로 이어지는 흐름을 실제 DB에 쿼리를 날려가며 따라가 봤는데, 그러다 결제가 반영되지 않는 버그를 하나 찾았습니다. 오늘 본 것 중 가장 중요한 항목이라 맨 앞에 두겠습니다.

> 참고: 스키마 파일 `lookpup.sql`이 있긴 한데, 실제 코드가 쓰는 컬럼/테이블과 어긋나는 부분이 꽤 됩니다(아래 1번). 그래서 ERD는 코드를 기준으로 다시 짰습니다.

---

## 0. [필수] 결제 웹훅이 항상 실패합니다 — 결제가 예약/정산에 반영 안 됨

`src/app/api/portone/webhook/route.ts:56-58`가 결제 건을 이렇게 찾습니다.

```ts
.from("payments").select(...).eq("payment_id", paymentId)
```

그런데 `payments` 테이블에는 `payment_id`라는 컬럼이 없습니다. PK가 `id`(포트원 결제 ID, text)예요. 이 조의 Supabase에 같은 쿼리를 직접 날려보니 이렇게 나옵니다.

```
GET /rest/v1/payments?select=payment_id  → HTTP 400
{"code":"42703","message":"column payments.payment_id does not exist"}
GET /rest/v1/payments?select=id,status    → HTTP 200  [{"id":"pay_1782115910913","status":"ready"}]
```

즉 포트원이 웹훅을 보낼 때마다 이 조회가 400으로 실패하고, 그 뒤에 와야 할 `payments.status = 'paid'`, `reservations.status = 'paid'` 갱신(`:70-71`)이 아예 실행되지 않습니다. 지금 DB에 결제 한 건이 `status: "ready"`로 멈춰 있는 게 바로 그 흔적입니다. 사용자 입장에선 결제가 끝났는데 예약은 계속 결제 전 상태로 남고, 정산도 잡히지 않는 거죠.

고치는 건 간단합니다. `.eq("payment_id", paymentId)`를 `.eq("id", paymentId)`로 바꾸면 됩니다(`:70,71,75,79`의 update는 이미 `.eq("id", ...)`로 맞게 돼 있고, 조회 한 줄만 어긋나 있습니다). 이렇게 한 글자 차이가 결제 흐름 전체를 끊어버리는 자리라, 이 흐름만큼은 테스트로 한 번 막아두면 좋겠습니다.

## 1. ERD — 스키마 파일과 실제 코드가 어긋납니다

`lookpup.sql`은 지금 그대로 믿고 쓰기 어려운 상태입니다. 코드엔 있는데 SQL엔 빠진 것들을 추려보면 이렇습니다.

- `chat_rooms.last_message` / `last_message_at`, `chat_rooms.owner_left` / `sitter_left`(채팅방 나가기) — `src/app/api/chat/rooms/route.ts:33,45,50`에서 쓰는데 SQL엔 없음
- `users.location_consent` — `src/app/petsitters/page.tsx:204` 사용, SQL엔 없음
- `reviews.image_urls`(복수 배열) — `src/app/actions/reviews.ts:97`에서 INSERT하는데 SQL은 `image_url`(단수, `lookpup.sql:180`). 컬럼명 자체가 달라 실제 INSERT가 깨질 수 있음
- `reservations.application_id` — `reservations/route.ts:60`에서 select하는데 SQL엔 없음

스키마 파일을 실제 DB에 맞춰 다시 뽑아두면(Supabase의 schema 추출), 다음에 ERD를 보고 작업할 때 헷갈릴 일이 없습니다. 핵심 관계 자체는 잘 잡혀 있습니다. `reservations`가 owner/sitter/service/request를 참조하고, `payments → reservations`로 이어지고, `reviews.reservation_id`(unique)로 예약당 리뷰 1개를 강제하는 설계는 도메인에 잘 맞습니다.

## 2. 느려질 만한 쿼리

### [필수] 지도·시터 목록이 전체를 받아 클라이언트에서 거릅니다 — `petsitters/page.tsx:148`, `api/sitters/route.ts:28-48`
지도는 `rpc("get_petsitters_for_map")`로 **승인된 시터를 인자 없이 전부** 받아온 다음, 거리 계산도 필터도 정렬도 전부 JS에서 합니다(`:312-337`). 시터 검색 API도 마찬가지로 `rpc("search_sitters_within")`로 반경 내 전체를 받은 뒤 `data.slice(offset, offset+limit)`로 JS에서 자릅니다(`route.ts:47-48`). 페이지네이션을 DB로 내리지 않으니, 2페이지를 보든 10페이지를 보든 매번 같은 전체 결과를 계산하고 전송하는 셈입니다. 시터가 수천 명까지 늘면 페이로드도 메모리도 렌더도 선형으로 무거워집니다. 위치 기반이라 더 까다로운 게, 좌표가 `numeric`이고 공간 인덱스(PostGIS/GiST)가 없어서 반경 검색을 DB가 인덱스로 가속해 줄 수도 없습니다. (여기에 `reviewCount: 0`으로 하드코딩해 두고 "리뷰 많은 순" 정렬을 거니, 값이 늘 0이라 정렬 자체가 의미가 없습니다 — `:168,333`.)

### [필수] 정산 합계가 최근 50건만 더해서 틀립니다 — `api/earnings/route.ts:44-67`
`payments`를 `sitter_id` + `status in (paid,ready)`로 거른 뒤 `limit(50)`을 걸고(`:47`), 그 50건을 JS `reduce`로 합산합니다(`:63,67`). 그래서 **결제가 50건을 넘는 시터는 정산 합계가 틀어집니다.** 정확성 버그이면서 동시에 성능 문제이기도 한데, 합계라는 건 본래 `SELECT SUM(settle_amount) ... GROUP BY date_trunc(...)`처럼 DB가 인덱스만 읽고 끝낼 일입니다. 지금은 행을 앱으로 다 끌어와 더하다 보니, 시터당 결제가 쌓일수록 느려지고 limit 때문에 값까지 틀리게 됩니다.

### [제안] 채팅방 목록 안읽음 수를 메시지 전건으로 셉니다 — `api/chat/rooms/route.ts:86-96`
방 목록을 가져온 다음, 모든 방의 안 읽은 메시지를 행 단위로 전부 받아와 JS로 셉니다. 안 읽은 메시지가 많아질수록 페이로드가 그만큼 커지고요. `SELECT room_id, COUNT(*) ... WHERE is_read=false GROUP BY room_id`처럼 DB가 세게 하면 숫자만 받아오면 됩니다.

### [제안] 구인게시판도 전체를 받아 클라에서 검색·페이지네이션 — `api/requests/route.ts:53-62`, `board/page.tsx:162-174`
`status=open` 글을 전부 반환한 다음, 카테고리·검색·페이지네이션을 클라이언트 `filter`+`slice`로 처리합니다. 글이 늘면 진입할 때마다 open 글을 통째로 받게 되고요. 검색·카테고리는 DB WHERE로, 페이지네이션은 DB range로 내려 주세요.

> 칭찬할 점도 하나 있습니다. 채팅 메시지·예약 목록은 `created_at` 기반 keyset(cursor) 페이지네이션에 `limit+1`까지 얹어 잘 구현해 두셨습니다(`chat/rooms/[id]/messages/route.ts:62-82`). 지난 회차에 짚었던 "채팅 메시지 페이지네이션 부재"가 이걸로 해소됐습니다. 잘 고치셨네요.

## 3. 보안 — service role 전면 사용

### [제안] 공개 데이터까지 전부 service role로 RLS를 우회합니다 — `utils/supabase/service.ts`
시터 목록·상세·구인글 같은 **공개 데이터 조회까지** service role 클라이언트로 합니다(`api/sitters/route.ts:26`, `api/requests/route.ts:19` 등). 코드 주석에도 "RLS SELECT 정책이 없어 anon이 0행이라 service client로 우회한다"고 적혀 있고요. anon 키로 `sitters`를 직접 읽어보니 정말 0행이 나왔습니다(공개 데이터인데도 막혀 있는 거죠).

문제는 service role이 **모든 행을 read/write할 수 있는 키**라는 데 있습니다. 지금 구조는 RLS를 보안 경계로 쓰지 않고 전부 우회한 다음 인가를 앱 코드(owner/sitter 체크)로만 거는 방식이라, 라우트 한 곳에서 owner 체크가 빠지는 순간 전체 데이터가 그대로 노출되거나 변조될 수 있습니다. 공개 데이터(시터 목록 등)는 anon SELECT RLS 정책을 제대로 살리고, service role은 웹훅처럼 꼭 필요한 곳으로 좁혀 쓰시길 권합니다. 이번에 새로 생긴 문제는 아니고 계속 남아 있는 설계 숙제이니, 시간 날 때 방향을 한번 정해 보면 좋겠습니다.

## 4. ERD로 본 비즈니스 관점

### [필수] 예약 시간대 중복을 막지 않습니다 — `actions/reservations.ts:39-52,148-161`
예약을 만들 때 같은 시터의 기존 예약과 시간이 겹치는지 검사하지 않고 바로 INSERT합니다. 스키마에도 시터 시간대 배타 제약이 없다 보니, **한 시터가 같은 시간에 여러 예약**을 받을 수 있습니다. 펫시터 매칭의 핵심이라 꼭 막아야 하는 부분입니다(막는 방법은 가이드에 정리해 뒀습니다).

### [제안] 수수료율이 스키마와 코드가 2배 다릅니다
`lookpup.sql:157`은 `fee_rate default 0.10`인데, 코드는 `FEE_RATE = 0.05`로 정산을 계산해 넣습니다(`actions/reservations.ts:6,76-78`). 정산 금액이 두 배나 차이 나니, 어느 쪽이 정책인지 정한 뒤 한쪽으로 통일해 주세요.

### [제안] 예약 상태 전이가 두 군데로 분산
앱의 `VALID_TRANSITIONS`(`reservations.ts:181-186`)에는 `pending→paid` 전이가 없는데, 정작 결제는 웹훅이 직접 `paid`로 raw update를 합니다(0번 버그를 고쳐야 비로소 동작하고요). 상태 변경 경로가 "앱 검증"과 "웹훅 직접 update" 둘로 나뉘어 있어서, 한쪽 검증을 우회할 여지가 생깁니다. 결제 확정도 같은 상태머신을 거치도록 한곳으로 모으면 더 안전합니다.

## 6. 팀 공통

- **스키마 파일(`lookpup.sql`)을 다시 뽑아 주세요.** 실제 DB와 컬럼·테이블이 여러 군데 어긋나 있어서(1번), ERD 산출물로 쓰려면 실 DB를 기준으로 새로 추출해야 합니다.
- **"전체 받아서 클라에서 처리"가 반복됩니다.** 지도, 시터 검색, 게시판, 안읽음 카운트가 다 그렇습니다. 필터·정렬·페이지네이션·집계는 DB로 내리는 걸 팀 공통 습관으로 잡으면 좋겠습니다.
- **결제 흐름은 테스트로 지켜 주세요.** 0번처럼 한 글자가 전체 흐름을 끊어버리는 자리는, 작게라도 통합 테스트를 붙여두면 다음에 다시 깨질 일이 없습니다.

## 7. E2E 결과 (2026-06-23)

실제 앱을 띄워(포트 3300) 공개 동선을 따라가 봤습니다.

- 메인 `/`: HTTP 200 정상 (`review/images/2026-06-23/lookpup-01-main.png`)
- 펫시터 목록 `/petsitters`: HTTP 200, 목록은 뜨는데 지도 영역만 빈 화면 (`lookpup-02-petsitters.png`)
- 구인게시판 `/board`: HTTP 200 정상 (`lookpup-03-board.png`)

지도가 빈 화면으로 나온 건 카카오맵 도메인에 리뷰용 포트(3300)가 등록돼 있지 않아서입니다(콘솔에 kakao SDK 관련 에러가 찍힙니다). 코드 문제가 아니라 도메인 등록의 한계라, 지도 동작 자체는 확인하지 못했다는 점을 밝혀 둡니다. 로그인은 Google/Kakao OAuth뿐이라 자동화에서는 제외했고, 결제 흐름은 위 0번처럼 실제 DB 쿼리로 검증했습니다.
