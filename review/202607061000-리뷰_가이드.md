## 1. 공개 RPC 개인정보 3필드 제거 (제일 먼저 · DB만 바꾸면 끝)

### 왜 문제인가

`get_petsitters_filtered`는 펫시터 지도/목록을 그리는 함수인데, 로그인 없이(anon 키로) 호출해도 이렇게 나옵니다.

```json
{ "user_id": "a798ddcc-...", "full_name": "박규나",
  "available_area": "광주광역시 북구 동문대로249번길 12", ... }
```

지도에 핀 하나 찍는 데 실명·로그인 UUID·번지까지 있는 전체 주소는 필요가 없습니다. 이건 RLS로도 못 막습니다 — 함수가 `SECURITY DEFINER`라 정책을 건너뛰고 실행되기 때문입니다. 그러니 **함수 반환 자체에서 필요 없는 컬럼을 빼는 것**이 정답입니다.

### 어떻게 고치나

Supabase 대시보드 SQL Editor(또는 마이그레이션)에서 함수를 다시 정의하면서 `full_name`·`user_id`·`available_area` 세 컬럼을 빼면 됩니다. 지도/목록은 `display_area`(구·동 단위)와 fuzz 좌표만으로 충분합니다.

```sql
create or replace function get_petsitters_filtered(
  p_district text default null,
  p_dong text default null
)
returns table (
  id uuid,
  -- user_id  ← 제거
  -- full_name ← 제거
  -- available_area ← 제거 (전체 주소)
  display_area text,      -- 구·동 단위만 유지
  latitude double precision,
  longitude double precision,
  base_price integer,
  rating numeric,
  service_types text[],
  profile_image text
)
language sql
security definer
set search_path = public
as $$
  select s.id, s.display_area, s.latitude, s.longitude,
         s.base_price, s.rating, s.service_types, u.profile_image
  from sitters s
  join users u on u.id = s.user_id
  where s.status = 'approved'
    and (p_district is null or s.district = p_district)
    and (p_dong is null or s.dong = p_dong);
$$;
```

> 시터 이름을 목록 카드에 꼭 보여줘야 한다면, 실명 대신 **닉네임 컬럼**을 따로 두거나, 상세 페이지 진입 시 로그인된 사용자에게만 별도 함수로 내려주는 방식을 권합니다. 목록 단계에서 실명을 다 뿌리는 건 크롤링에 그대로 노출됩니다.

컬럼을 뺐으면 프론트 타입도 맞춰야 합니다. `npx supabase gen types typescript`로 `database.types.ts`를 다시 뽑고, `useSitters.ts`에서 `full_name`을 쓰던 부분이 있으면 정리해 주세요.

### 확인

```bash
curl -s -X POST "$SUPABASE_URL/rest/v1/rpc/get_petsitters_filtered" \
  -H "apikey: $ANON_KEY" -H "Content-Type: application/json" -d '{}'
```

응답에 `full_name`·`user_id`·`available_area`가 더 이상 없으면 닫힌 겁니다.

## 2. 결제 금액 서버 재계산 (제일 위험 · createPayment 한 곳)

### 왜 문제인가

`payments.ts:86`이 이렇습니다.

```ts
const amount = requestedAmount ?? reservation.total_price;   // 클라 금액을 그대로 신뢰
// ...
if (requestedAmount && requestedAmount !== reservation.total_price) {
  await db.from("reservations")
    .update({ total_price: requestedAmount })   // 예약가까지 클라 값으로 덮음
    .eq("id", reservationId);
}
```

`ChatClient.tsx:828`이 `createPayment(reservationId, "CARD", totalAmount)`로 부르는데, 이 `totalAmount`가 브라우저에서 온 값입니다. 그러니 개발자도구에서 `createPayment(myId, "CARD", 1)`을 부르면 1원이 저장되고, 포트원 1원 결제 → 웹훅이 "저장값(1) == 결제값(1)"로 통과시킵니다. 금액 대조가 "저장된 값끼리"라 처음부터 낮게 저장하면 검증을 그냥 지나가는 구조예요.

이미 여러분은 정답을 알고 있습니다 — 채팅 나가기를 `chat.ts`에서 서버가 최종 판단하게 막았고(b552772), 예약 금액도 `createPetsitterReservationRequest`에서 서버가 `service.price × days`로 계산합니다(010f404). **결제만 이 원칙에서 빠져 있는 것**이라, 같은 원칙을 여기에도 적용하면 됩니다.

### 어떻게 고치나

`createPayment`가 `requestedAmount`를 **믿지 말고 무시**하고, 예약의 실제가를 서버에서 다시 확정하도록 바꿉니다. 추가금은 이미 `createExtraPayment`가 따로 처리하니, 최초 결제는 예약가 그대로면 됩니다.

```ts
export async function createPayment(
  reservationId: string,
  payMethod: "CARD" | "VIRTUAL_ACCOUNT" | "TRANSFER",
  // requestedAmount 파라미터는 받지 않거나, 받더라도 쓰지 않습니다.
) {
  // ... 인증 · 예약 조회 · owner 확인 · status === "accepted" 확인 (기존 그대로)

  // 금액은 서버가 진실. 클라가 준 값은 절대 신뢰하지 않는다.
  const amount = reservation.total_price;

  // total_price 를 클라 값으로 덮어쓰던 91~96 블록은 통째로 삭제합니다.

  const platformFee = Math.floor(amount * FEE_RATE);
  const settleAmount = amount - platformFee;
  // ... insert 는 기존 그대로 (amount 는 위에서 확정한 서버 값)
}
```

그리고 호출부 `ChatClient.tsx:828`에서 세 번째 인자(`totalAmount`)를 빼 줍니다.

```ts
const payResult = await createPayment(reservationId, "CARD");
```

`payment/page.tsx:80`은 이미 `createPayment(reservationId, "CARD")`로 부르고 있어 그대로 두면 됩니다.

> 만약 "부분 결제"나 "쿠폰 적용"처럼 금액이 예약가와 달라져야 하는 경우가 있다면, 그 할인/차감 계산도 **서버에서** 하세요. 클라가 최종 금액을 통보하는 구조만 아니면 됩니다.

### 확인

로그인 상태에서 개발자도구 콘솔로 `createPayment(내예약id, "CARD", 1)`을 흉내 내 호출하거나, `payments` 테이블에 저장된 `amount`가 예약가와 같은지 봅니다. 1이 아니라 예약 실제가로 저장되면 닫힌 겁니다. (실 결제까지 가지 말고 저장값만 확인하면 충분합니다.)

## 3. 자기 예약 차단 (내일 · 두 함수에 한 줄씩)

### 왜 문제인가

`createReservation`(reservations.ts:35~)과 `createPetsitterReservationRequest`(:845~) 둘 다 서비스 존재·가격은 확인하지만, **예약하는 사람이 그 시터 본인인지**는 안 봅니다. UI에서 `isSelf`로 버튼을 숨겨도, 서버 액션을 직접 부르면 자기 자신에게 예약이 생깁니다. 시연 중에 우연히 자기 계정으로 자기한테 예약이 잡히면 데이터도 지저분해지고요.

### 어떻게 고치나

두 함수 모두 서비스 조회 뒤(시터 `user_id`를 알 수 있는 지점)에 한 줄 가드를 넣습니다. 서비스 조회 쿼리에 시터의 `user_id`를 함께 가져오면 됩니다.

```ts
// services 조회할 때 시터의 user_id 를 같이 가져온다
const { data: service } = await db
  .from("services")
  .select("id, sitter_id, price, is_active, sitters!inner(user_id)")
  .eq("id", input.service_id)
  .single();

// ... 기존 존재/가격 검증 이후

const sitterUserId = (service.sitters as { user_id: string }).user_id;
if (sitterUserId === user.id) {
  return {
    error: { code: "FORBIDDEN", message: "본인에게는 예약할 수 없습니다." },
  };
}
```

두 함수에 같은 가드를 넣어 주세요. 여유가 되면 예약에 넣은 반려동물(`pet_ids`)이 정말 본인 소유인지도 한 번 확인하면 더 단단합니다 — `pets` 테이블에서 `id in (pet_ids)` 이면서 `owner_id === user.id`인 행 수가 `pet_ids.length`와 같은지 보면 됩니다.

### 확인

자기 계정으로 자기 시터 프로필에 예약을 시도했을 때 `FORBIDDEN`이 돌아오면 닫힌 겁니다.
