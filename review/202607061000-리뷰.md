# lookpup(봐주개) 19차 코드 리뷰 (2026-07-06)

발표가 이틀 뒤 수요일이라, 이번 리뷰는 "새로 뭘 봤나"보다 **공개 전에 반드시 닫아야 하는 보안 세 가지**에 초점을 맞췄습니다. 18차(7/4) 이후 dev에 커밋이 60개 넘게 쌓였는데, 새 라우트를 여는 커밋은 하나도 없고 전부 기존 화면을 다듬거나 고치는 작업이었습니다 — 채팅방 나가기 차단, 예약 금액 계산, 호텔 필터 정리, 보호자 프로필 사진 연결, lint 정리, 페이지 애니메이션 등이요. 마감 직전에 이렇게 "새 기능을 안 열고 있던 걸 단단히 하는" 방향은 아주 좋은 판단이라 생각합니다.

먼저 결론부터 말하면, 지난번에 짚었던 보안 세 가지(1원 결제·공개 RPC 개인정보·자기 예약)는 **셋 다 아직 열려 있습니다.** 그중 공개 RPC 개인정보는 이번에도 실제로 anon 키로 찔러서 실명·주소가 그대로 나오는 걸 확인했습니다. 이 세 개만 이틀 안에 닫으면 레포를 공개해도 부끄럽지 않은 상태가 됩니다. 아래는 지난 반영 현황을 먼저 보고, E2E와 멤버별, 팀 공통을 거쳐 마무리 우선순위로 맺는 순서로 정리했습니다.

## 3. 멤버별

### 영은 (0sliverchoi321z) — 채팅·결제

이번 회차 커밋 대부분이 영은 손에서 나왔습니다. 특히 **채팅방 나가기 차단(b552772)을 서버에서 막은 게 정석입니다(칭찬).** `chat.ts`의 `sendMessage`·`sendImageMessage` 두 군데에 `isRecipientActive` 가드를 넣어서, 상대가 나간 방이면 서버 액션이 `RECIPIENT_LEFT`로 되돌려 보냅니다. 클라에서 버튼만 숨긴 게 아니라 서버가 최종 판단을 하니, URL이나 직접 호출로도 우회가 안 됩니다. 이게 바로 아래에서 이야기할 결제 문제의 정답이기도 합니다.

그런데 **같은 "서버가 최종 판단" 원칙이 결제에는 빠져 있습니다.** `payments.ts:86`의 `createPayment`가 클라에서 넘어온 `requestedAmount`를 그대로 믿고, 심지어 `reservations.total_price`까지 그 값으로 덮어씁니다(91~96). 호출부인 `ChatClient.tsx:828`이 `createPayment(reservationId, "CARD", totalAmount)`로 부르는데, 이 `totalAmount`는 브라우저에서 계산된 값이라, 예약 owner가 개발자도구로 `createPayment(myId, "CARD", 1)`을 부르면 1원이 저장되고 포트원 1원 결제 → 웹훅이 "저장값(1) == 결제값(1)"로 통과시켜 결제완료가 됩니다. 채팅 나가기를 서버에서 막았듯, **결제 금액도 서버가 예약 실제가로 다시 계산**하게 한 줄만 바꾸면 이 구멍이 닫힙니다. 해결은 가이드 1번에 코드로 적어 뒀습니다. `[필수]`

## 4. 팀 공통

- **결제는 "서버가 금액의 기준"이어야 합니다.** 채팅 나가기를 서버에서 막은 것과 똑같은 원칙입니다. 웹훅에 금액 대조를 넣어 둔 건 좋지만, 그 대조가 "저장된 값끼리"라서 처음부터 1로 저장되면 그냥 통과합니다. `createPayment`가 예약의 실제가(서비스 가격 × 일수 + 승인된 추가금)로 다시 계산하는 지점 하나만 넣으면 방어가 닫힙니다.
- **공개 RPC에서 개인정보 3필드 제거.** `get_petsitters_filtered`의 `full_name`·`user_id`·`available_area`만 빼면 됩니다. 이건 코드 배포가 아니라 DB 함수 하나만 바꾸는 거라, 셋 중 제일 빨리 닫을 수 있습니다.
- **자기 예약은 서버 액션에서 한 줄로 막습니다.** UI(`petsitters/[id]`의 isSelf)만으로는 API 직접 호출을 못 막습니다. 두 예약 함수에 시터의 `user_id === user.id`면 거절하는 가드를 넣어 주세요.
- **정리해서 좋았던 것들.** 채팅 나가기 서버 차단, 예약 금액 서버 계산, eslint 12건 감소, 새 기능 동결 후 안정화로 방향을 튼 것 — 마감 앞 판단으로 아주 적절합니다.

## 5. 우리 조 마무리 우선순위 (이틀 안에 보안 3종 닫기)

발표까지 코드를 만질 수 있는 날이 오늘·내일 이틀뿐이라, 순서를 이렇게 잡으면 좋겠습니다. 세 개 다 "한 곳만 고치면 되는" 작은 수술이라 이틀이면 충분합니다.

1. **오늘 오전 — 공개 RPC 개인정보 3필드 제거(가장 빠름·실명/주소 노출).** DB 함수 하나만 바꾸면 됩니다. 배포 없이 즉시 닫힙니다.
2. **오늘 오후 — 결제 서버 재계산(가장 위험).** `createPayment`에서 `requestedAmount` 신뢰를 걷어내고 예약 실제가로 계산. 1원 결제가 재현 안 되는지 다시 확인.
3. **내일 오전 — 자기 예약 가드(한 줄).** 두 예약 함수에 시터==본인 거절 추가.
4. **내일 오후 — 검증·동결.** 세 개 다 닫힌 걸 확인한 뒤로는 코드를 더 만지지 않습니다. E2E 한 번 더 돌려 라우트가 안 깨졌는지만 봅니다.

여유가 되면 GoTrueClient 하나로 합치기·reviews 응답의 UUID 제거·정산 undefined 정규화까지 손대면 레포가 한층 깔끔해집니다. 다만 이건 보안 3종을 닫은 다음입니다. 자세한 해결 코드는 함께 드리는 가이드에 담아 뒀습니다. 화이팅입니다.
