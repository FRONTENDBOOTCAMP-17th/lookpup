## 1. 회원탈퇴 실제 연결 [필수·이월]

증상: 탈퇴 확인을 눌러도 "완료" 화면만 뜨고 계정은 그대로 남아 있습니다.
원인: `myprofile/settings/withdraw/page.tsx`의 `handleDelete`가 `setDone(true)`까지만 하고 끝나기 때문입니다.

이미 만들어 둔 `deleteUser()` 액션을 연결하기만 하면 됩니다. 탈퇴는 되돌릴 수 없는 동작이라, 호출하고 성공을 확인한 뒤 로그아웃하고 안내하는 순서로 묶어 주세요.

```tsx
'use client';
import { deleteUser } from '@/app/actions/user';   // 이미 있는 액션
import { createClient } from '@/utils/supabase/client';
import { useRouter } from 'next/navigation';

const router = useRouter();
const [deleting, setDeleting] = useState(false);
const [error, setError] = useState<string | null>(null);

const handleDelete = async () => {
  if (deleting) return;        // 중복 클릭 방지
  setDeleting(true);
  setError(null);
  try {
    const res = await deleteUser();
    if (!res?.success) {
      setError('탈퇴 처리에 실패했습니다. 잠시 후 다시 시도해주세요.');
      return;
    }
    await createClient().auth.signOut();   // 세션 정리
    setDone(true);                          // 완료 화면
    // 또는 router.replace('/?withdrawn=1');
  } catch {
    setError('탈퇴 처리 중 오류가 발생했습니다.');
  } finally {
    setDeleting(false);
  }
};
```

확인 버튼에는 `disabled={deleting}`을 걸어서 두 번 눌리지 않게 막아 주세요.

> 탈퇴할 때 같이 지워야 할 데이터(예약·결제·게시글 등)가 있다면 `deleteUser()` 액션 안에서 순서대로 정리하거나
> DB의 `on delete cascade`로 묶어 두면 됩니다. 이 부분이 까다로워서 미뤄둔 거라면 정리 방법부터 같이 정해 봐도 좋습니다.

## 2. 쓰기 페이지 로그인 가드 [제안]

`/board/write`·`/board/[id]/edit`가 비로그인 상태에서도 폼을 그대로 다 보여줍니다. 제출은 Server Action이 막아주긴 하지만,
사용자가 끝까지 다 채워 놓고 마지막 순간에 막히면 좀 아쉽지 않을까요. 진입할 때 한 번만 확인해 주면 됩니다.

클라이언트 컴포넌트라면 이미 쓰고 있는 `userStore`/`UserProvider`로 확인할 수 있습니다.

```tsx
'use client';
import { useEffect } from 'react';
import { useRouter } from 'next/navigation';
import { useUserStore } from '@/store/userStore';

const { user, isLoading } = useUserStore();
const router = useRouter();

useEffect(() => {
  if (!isLoading && !user) {
    router.replace('/login?next=/board/write');   // 로그인 후 돌아오게
  }
}, [isLoading, user, router]);

if (isLoading || !user) return null;   // 확인 전엔 폼을 그리지 않음
```

`isLoading`을 같이 보는 이유는, 인증 상태가 정해지기 전에 잠깐 비로그인으로 보였다가 깜빡이는 현상을 막기 위해서입니다
(7차에 칭찬했던 `isLoading` 초기 true 패턴과 같은 맥락이라고 보면 됩니다).

## 3. 조회 RLS 방향 정하기 [제안]

`/api/requests/[id]` GET이 `createServiceClient`(RLS 우회)로 조회하고 있습니다. 공개 게시판이라 지금 당장은 문제될 게 없지만,
"조회를 어디까지 service client로 우회할지"를 한 번 정해 두면 코드 전체가 일관되어집니다. 다음 두 가지 중 하나를 택하면 됩니다.

- (A) 공개 데이터는 `requests` 테이블에 anon SELECT 정책을 열고, 조회 API도 anon 클라이언트로 바꾼다 — RLS가 실제 방어선이 됨.
- (B) 계속 service client로 조회하되, **노출해도 되는 컬럼만 select** 한다(지금 `users!owner_id(full_name, profile_image, is_verified)`처럼).

지금 코드는 (B)에 가깝습니다. 이 경우 "왜 service client로 읽는가(= RLS 우회가 의도다)"를 주석 한 줄로 남겨 두면 다음에 이 코드를 볼 사람이 헷갈리지 않습니다.

## 4. API 에러 메시지 래핑 [제안]

`/api/requests/[id]` GET의 에러 응답입니다.

```ts
// 지금
return NextResponse.json({ error: { code: "INTERNAL_ERROR", message: error.message } }, { status: 500 });

// 제안 — 원문은 로그로
console.error('[GET /api/requests/:id]', error.message);
return NextResponse.json({ error: { code: "INTERNAL_ERROR", message: "요청을 불러오지 못했습니다." } }, { status: 500 });
```

---

정리하면 **1번(회원탈퇴 연결)** 이 여러 회차째 이어진 [필수]라, 이번엔 꼭 닫고 갑시다.
나머지(2~4)는 권장 사항이니 1번부터 끝낸 다음 여유가 생기는 대로 하나씩 가면 됩니다.
