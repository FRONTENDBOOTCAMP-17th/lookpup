# lookpup(봐주개) 14차 리뷰 — 공개 페이지 SEO 점검 + 결제 보안

작성: 2026-06-29 / 대상 브랜치: dev / 범위: 12차(2026-06-24) 머지 이후 dev에 올라온 변경

이번 회차는 검색엔진에 노출돼야 하는 공개 페이지의 SEO 상태를 전수로 점검하고, 그와 별개로 결제 흐름에서 한 군데 보안 구멍을 찾아 정리했습니다. 한 가지 미리 밝혀 두면, 이번엔 라이브 E2E(브라우저 자동화)는 돌리지 않고 **정적 검증(코드 + 샘플 응답 구조) 기준**으로 봤습니다. 공개 페이지의 SSR/CSR 여부는 화면이 아니라 서버가 내려주는 HTML 구조에서 갈리는 문제라 코드만으로도 충분히 확정할 수 있어서입니다.

## 2. 이번 핵심 한눈에

1. **공개 페이지 SEO가 다섯 조 중 가장 약합니다.** 검색에 걸려야 할 목록·상세 페이지가 전부 `'use client'` + `useEffect` 패칭이라, 크롤러가 받아 가는 HTML이 비어 있습니다.
2. **standalone `/payment` 페이지에 금액 조작 취약점**이 있습니다. URL의 `?amount=` 값을 그대로 결제 금액으로 쓰고, `payments` 행을 만들지 않습니다.
3. SEO 토대(`metadataBase`, `sitemap.ts`, `robots.ts`)가 아직 없습니다.

## 3. 공개 페이지 SEO 점검

검색엔진은 사람이 보는 화면이 아니라 **서버가 내려준 HTML 원문**을 읽습니다. 그래서 공개 페이지(메인·목록·상세)는 서버에서 데이터를 받아 HTML에 담아 내려보내야 색인이 됩니다. 그런데 봐주개의 공개 페이지는 메인을 빼면 전부 클라이언트에서 데이터를 가져오는 구조라, 봇이 받는 첫 HTML에는 게시글 제목도, 펫시터 이름도 들어 있지 않습니다.

| 페이지 | 렌더링 | 데이터 패칭 | SEO 상태 |
|---|---|---|---|
| `/` (홈) | **SSR** | 정적/더미 | 양호 (다만 페이지별 메타 없음) |
| `/about` (소개) | **SSR** | 정적 | 양호 (메타만 보강하면 됨) |
| `/board` (구인 목록) | CSR | `useEffect` → `fetch('/api/requests?status=open')` (`board/page.tsx:1, 132`) | **빈 HTML로 색인** |
| `/board/[id]` (구인 상세) | CSR | `useEffect` → `fetch('/api/requests/${id}')` (`board/[id]/page.tsx:1, 147`) | **빈 HTML로 색인** |
| `/petsitters` (시터 목록) | CSR | `useEffect` → `supabase.rpc('get_petsitters_for_map')` (`petsitters/page.tsx:1, 152`) | **빈 HTML로 색인** |
| `/petsitters/[id]` (시터 상세) | CSR | `useEffect` → `supabase.rpc('get_petsitter_detail')` (`petsitters/[id]/page.tsx:1, 73`) | **빈 HTML로 색인** |

`[필수/SEO]` **목록·상세 네 페이지를 서버 컴포넌트로 전환**해 주세요. 이게 이번 SEO의 가장 큰 문제입니다. 봐주개의 핵심 콘텐츠인 구인글과 펫시터 프로필이 검색에 전부 빈 페이지로 잡힙니다. 사용자가 구글에서 "○○동 펫시터"를 검색해도 우리 시터 상세가 안 걸리는 셈이라, 서비스 성격상 손해가 큽니다. 데이터는 서버에서 받아 HTML에 박고, 지도·필터처럼 상호작용이 필요한 부분만 `'use client'` 자식 컴포넌트로 떼어내는 패턴으로 가면 됩니다. 구체적인 전환 방법은 같은 날짜의 `_가이드.md`에 단계별로 적어 뒀습니다.

`[필수/SEO]` **루트 `layout.tsx`에 `metadataBase`가 없습니다**(`layout.tsx:19~22`). title·description은 들어 있고 `lang="ko"`도 맞게 돼 있는데(잘하셨습니다), `metadataBase`가 없으면 OG 이미지·canonical을 절대경로로 못 만들어 카카오톡·SNS 미리보기가 깨집니다. `openGraph`/`twitter`/`alternates`도 아직 비어 있습니다.

`[필수/SEO]` **`generateMetadata`가 한 군데도 없습니다.** 그래서 모든 구인글 상세, 모든 시터 상세가 "봐주개 - 믿을 수 있는…"이라는 **하나의 제목**을 공유합니다. 상세 페이지를 서버 컴포넌트로 바꾸는 김에 `generateMetadata`로 글/시터마다 제목·설명이 달라지게 해 주세요.

`[필수/SEO]` **`sitemap.ts`도 `robots.ts`도 없습니다.** 크롤러에게 공개 URL 목록과 출입 규칙을 알려주는 파일입니다. `sitemap.ts`에 홈·목록·상세를 넣고, `robots.ts`에서 `/admin`·`/myprofile`·`/chat`·`/payment`·`/auth`를 disallow로 막아 주세요.

참고로 인증 전용 페이지(`/chat`, `/myprofile/*`, `/admin/*`, `/payment/*`, `board/write`, `board/[id]/edit`, `sitter-register`, `pet-register`, `notifications`, `auth/*`)는 반대로 **검색에서 빼야** 하는 쪽이라, 이쪽엔 `robots: { index: false }`를 주는 게 맞습니다. 공개와 비공개를 가르는 기준은 가이드와 같이 공유한 SEO 가이드 글 8장에 정리돼 있습니다.

`[필수/보안 — 중대]` 그런데 **standalone `src/app/payment/page.tsx`는 이 안전한 경로를 타지 않습니다.** 이 페이지는 결제 금액을 URL 쿼리에서 그대로 읽고(`amount = Number(searchParams.get("amount") ?? 35000)`, `payment/page.tsx:57`), 클라이언트가 만든 `paymentId: pay_${Date.now()}`로 PortOne에 `totalAmount`를 직접 던집니다(`payment/page.tsx:83~85`). 결정적으로 이 페이지는 **`createPayment`를 한 번도 호출하지 않아서**(파일 전체에 호출이 없습니다) `payments` 행이 생기지 않습니다. 그러면 웹훅이 그 결제 ID로 행을 찾지 못해 조용히 `200 { ok: true }`만 돌려주고 끝납니다(`webhook/route.ts:62~64`). 결과적으로 누구든 `/payment?amount=1`로 들어가 **1원 결제**를 시도할 수 있고, 게다가 고객 정보가 `"테스트"/010-0000-0000/test@test.com`으로 하드코딩돼 있습니다(`payment/page.tsx:90~92`). 채팅 플로우(`chat/page.tsx`)가 이미 올바른 본보기이니, 이 standalone 페이지를 거기에 맞춰 `createPayment` 경유로 고치거나(금액을 서버에서 도출), 더 이상 쓰지 않는다면 페이지 자체를 지우는 쪽이 깔끔합니다. 해결 코드는 가이드 1장에 적었습니다.

`[제안]` `createPayment`(`actions/payments.ts:97`)의 `sitter_id: (reservation as unknown as { sitter_id: string }).sitter_id`는 이중 캐스팅으로 타입을 가리고 있습니다. `database.types`를 갱신해 reservation 행에서 `sitter_id`가 제대로 추론되게 하면 `as unknown` 우회를 걷어낼 수 있습니다.

`[사소]` 머지 과정에서 settings 페이지의 `activeTab` 기본값이 `"notifications"`로 돼 있습니다(`myprofile/settings/page.tsx:61`). 의도한 기본 탭이 맞는지만 한 번 확인해 주세요.

## 5. 팀 공통

- **결제 진입점이 두 갈래라는 게 이번 핵심 위험입니다.** 채팅 경로는 서버 검증을 거치는데 standalone `/payment`는 안 거칩니다. 같은 도메인 로직(결제 행 생성·금액 도출)이 한 곳(서버 액션)으로 모이게 정리하면, 진입점이 늘어도 안전성이 유지됩니다. 지금처럼 페이지마다 결제 호출을 따로 만들면 한쪽만 안전한 상황이 반복됩니다.
- **SEO 토대는 한 번 깔면 끝나는 일**입니다. `metadataBase`·`sitemap.ts`·`robots.ts`는 페이지 수와 무관하게 파일 세 개로 끝나니, 목록·상세 서버 전환과 함께 이번에 같이 정리해 두면 좋겠습니다.
- 분담은 결제(gyuhwa)·채팅·예약 플로우(0sliverchoi321z)·후기/변수정리(박규나)·알림(BestSeal)로 비교적 고르게 나뉘어 있습니다. 결제처럼 한 도메인을 여러 명이 건드리는 부분은, 진입점·서버 액션을 누가 단일 소스로 관리할지 한 번 합의해 두면 위 같은 이원화를 막을 수 있을 듯합니다.
