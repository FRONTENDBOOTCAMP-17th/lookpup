# lookpup 14차 해결 가이드 — 결제 보안 + 공개 페이지 SEO

리뷰에서 짚은 `[필수]`들을 어떻게 고치는지 단계별로 적었습니다. SEO 개념 자체(크롤러가 무엇을 보는지, 서버/클라이언트 렌더링 차이, metadata API 등)는 따로 공유한 **`seo-가이드.md`**(블로그에도 올려 둔 글)에 처음부터 정리돼 있으니, 헷갈리는 부분은 거기 장 번호를 같이 짚어 가며 보면 됩니다.

---

## 1. `/payment` 금액 조작 막기 — 서버에서 금액을 도출한다

### 지금 무엇이 문제인가

`src/app/payment/page.tsx`는 결제 금액을 URL에서 그대로 읽습니다.

```tsx
// payment/page.tsx:57
const amount = Number(searchParams.get("amount") ?? 35000);
// ...
const handlePay = () => {
  requestPayment({
    paymentId: `pay_${Date.now()}`,   // 클라이언트가 만든 ID
    totalAmount: total,                // 클라이언트가 정한 금액
    customer: { fullName: "테스트", phoneNumber: "010-0000-0000", email: "test@test.com" },
    // ...
  });
};
```

이러면 `/payment?amount=1`로 들어온 사람이 1원을 결제할 수 있고, 게다가 `payments` 행이 안 생기니 웹훅도 이 결제를 못 알아봅니다.

### 이미 올바른 본보기가 팀 안에 있습니다

채팅 결제는 이렇게 **먼저 서버에서 결제 행을 만들고**, 거기서 돌려준 금액·ID로 PortOne을 호출합니다.

```tsx
// chat/page.tsx:374~382 — 이게 정석입니다
if (reservationId) {
  const payResult = await createPayment(reservationId, "CARD");
  if (payResult.error) { /* 실패 처리 */ return; }
  portonePaymentId = payResult.data!.payment_id;  // 서버가 만든 ID
  totalAmount      = payResult.data!.amount;       // 서버가 계산한 금액
  orderName        = payResult.data!.order_name;
}
requestPayment({ paymentId: portonePaymentId, totalAmount, /* ... */ });
```

### 고치는 두 가지 방법

**방법 A — 페이지를 제거한다 (가장 깔끔)**
채팅·게시판에서 결제로 진입하는 경로가 모두 채팅 플로우(또는 동일한 `createPayment` 경유)를 탄다면, standalone `/payment/page.tsx`는 더 이상 쓰지 않는 페이지일 수 있습니다. 어디서도 `/payment?...`로 직접 링크하지 않는지 확인하고(`grep -rn "/payment?" src/`), 쓰는 데가 없으면 페이지를 지우는 게 가장 안전합니다.

**방법 B — 채팅 플로우와 똑같이 맞춘다**
이 페이지를 꼭 유지해야 한다면, URL의 `amount`를 신뢰하지 말고 **예약 id만 받아 서버에서 금액을 도출**하게 바꿉니다.

```tsx
// payment/page.tsx — handlePay 안
const handlePay = async () => {
  const reservationId = searchParams.get("reservationId");
  if (!reservationId) { /* 잘못된 진입 처리 */ return; }

  // 금액·ID·주문명은 전부 서버에서 (URL amount 사용 금지)
  const payResult = await createPayment(reservationId, "CARD");
  if (payResult.error) {
    // 모달/토스트로 실패 안내
    return;
  }
  requestPayment({
    paymentId:   payResult.data!.payment_id,
    totalAmount: payResult.data!.amount,
    orderName:   payResult.data!.order_name,
    currency: "KRW",
    payMethod: "CARD",
    redirectUrl: `${window.location.origin}/payment/complete`,
    customer: { /* 로그인 사용자 실제 정보로 */ },
  }, { onSuccess, onFail });
};
```

핵심은 **금액의 진실을 서버가 쥐는 것**입니다. 클라이언트가 금액을 정하는 구조는, 사용자가 개발자도구로 값을 바꿀 수 있는 한 어떤 검증을 붙여도 결국 뚫립니다. 고객 정보 `"테스트"/010-0000-0000/test@test.com` 더미도 로그인 사용자 실제 값으로 바꿔 주세요(운영에서 유출됩니다).

## 2. 공개 목록·상세 페이지 서버 컴포넌트로 전환 (`seo-가이드.md` 0·2장)

`/board`, `/board/[id]`, `/petsitters`, `/petsitters/[id]` 네 페이지가 대상입니다. 패턴은 똑같습니다 — **데이터는 서버에서 받아 HTML에 담고, 상호작용이 필요한 부분만 클라이언트 자식으로 떼어냅니다.**

### 전환 전 (지금)

```tsx
// board/page.tsx:1
"use client";
export default function BoardPage() {
  const [posts, setPosts] = useState([]);
  useEffect(() => {                          // 크롤러는 빈 화면을 봅니다
    fetch("/api/requests?status=open").then(r => r.json()).then(setPosts);
  }, []);
  return <BoardList posts={posts} /* 필터·정렬 등 인터랙션 */ />;
}
```

### 전환 후

```tsx
// board/page.tsx — 'use client' 제거, async 서버 컴포넌트
import { createClient } from "@/lib/supabase/server";
import BoardListClient from "./BoardListClient";

export default async function BoardPage() {
  const supabase = await createClient();
  const { data: posts } = await supabase
    .from("requests")
    .select("*")
    .eq("status", "open");                    // 서버에서 직접 조회

  return <BoardListClient initialPosts={posts ?? []} />;  // HTML에 데이터가 담겨 내려감
}
```

```tsx
// board/BoardListClient.tsx — 필터·정렬·검색 같은 상호작용만 여기로
"use client";
export default function BoardListClient({ initialPosts }) {
  const [filter, setFilter] = useState("all");
  // 검색·정렬 UI ... (초기 목록은 이미 서버가 그려 줬으니 깜빡임도 없음)
}
```

`/petsitters`처럼 지도가 끼어 있는 페이지도 같은 방식입니다. **목록 데이터는 서버에서 받아 HTML에 담고**, 카카오 지도·마커처럼 브라우저에서만 도는 부분만 `'use client'` 자식에 둡니다. `supabase.rpc('get_petsitters_for_map')` 호출을 서버 컴포넌트로 올리면 됩니다.

상세 페이지(`board/[id]`, `petsitters/[id]`)도 똑같이 `async` 서버 컴포넌트로 바꾸고, 없는 데이터는 `notFound()`로 404를 내려 줍니다(soft-404 방지, 가이드 2장).

```tsx
// petsitters/[id]/page.tsx
import { notFound } from "next/navigation";
import { getSitter } from "@/lib/sitters";   // React.cache로 감싸면 메타+본문 1회 조회 (가이드 9장)

export default async function SitterDetail({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;               // Next 15+: params는 Promise라 await
  const sitter = await getSitter(id);
  if (!sitter) notFound();
  return <main><h1>{sitter.name}</h1>{/* ... */}</main>;
}
```

### `generateMetadata`로 상세마다 다른 제목 (가이드 2장)

지금은 모든 상세가 같은 제목을 씁니다. 상세 페이지에 이걸 추가하면 글·시터마다 제목이 달라집니다.

```tsx
export async function generateMetadata({ params }: { params: Promise<{ id: string }> }): Promise<Metadata> {
  const { id } = await params;
  const sitter = await getSitter(id);
  if (!sitter) return { title: "펫시터를 찾을 수 없습니다" };
  return {
    title: `${sitter.name} 펫시터`,
    description: (sitter.intro ?? "").slice(0, 120) || `${sitter.name} 펫시터 프로필`,
    alternates: { canonical: `/petsitters/${id}` },
    openGraph: {
      title: `${sitter.name} 펫시터`,
      images: sitter.profileImage ? [{ url: sitter.profileImage }] : [],
    },
  };
}
```

## 3. SEO 토대 3종 — `metadataBase` + `sitemap.ts` + `robots.ts` (가이드 1·6·7장)

### 루트 `layout.tsx`에 `metadataBase` 보강

지금 title·description·`lang="ko"`는 잘 돼 있습니다. `metadataBase`와 OG 기본값만 채우면 됩니다.

```tsx
// layout.tsx
export const metadata: Metadata = {
  metadataBase: new URL(process.env.NEXT_PUBLIC_SITE_URL ?? "http://localhost:3000"),
  title: {
    default: "봐주개 - 믿을 수 있는 반려동물 돌봄 플랫폼",
    template: "%s | 봐주개",        // 하위 페이지 제목 뒤에 자동으로 " | 봐주개"
  },
  description: "지역 기반 검색으로 가까운 펫시터를 찾고, 안전한 예약과 결제까지 한 번에",
  openGraph: { type: "website", siteName: "봐주개", locale: "ko_KR" },
};
```

### `app/sitemap.ts` — 공개 URL만

```ts
// src/app/sitemap.ts
import type { MetadataRoute } from "next";
import { createClient } from "@/lib/supabase/server";

const BASE = process.env.NEXT_PUBLIC_SITE_URL ?? "http://localhost:3000";

export default async function sitemap(): Promise<MetadataRoute.Sitemap> {
  const supabase = await createClient();
  const { data: posts } = await supabase.from("requests").select("id").eq("status", "open");
  const { data: sitters } = await supabase.from("sitters").select("id");

  return [
    { url: BASE, changeFrequency: "daily", priority: 1 },
    { url: `${BASE}/board`, changeFrequency: "hourly", priority: 0.9 },
    { url: `${BASE}/petsitters`, changeFrequency: "daily", priority: 0.9 },
    { url: `${BASE}/about`, priority: 0.5 },
    ...(posts ?? []).map((p) => ({ url: `${BASE}/board/${p.id}`, priority: 0.7 })),
    ...(sitters ?? []).map((s) => ({ url: `${BASE}/petsitters/${s.id}`, priority: 0.8 })),
  ];
}
```

마이페이지·관리자·결제·채팅 같은 비공개는 **사이트맵에 넣지 않습니다**(검색에 노출될 이유가 없습니다).

### `app/robots.ts` — 비공개 영역 차단

```ts
// src/app/robots.ts
import type { MetadataRoute } from "next";
const BASE = process.env.NEXT_PUBLIC_SITE_URL ?? "http://localhost:3000";

export default function robots(): MetadataRoute.Robots {
  return {
    rules: {
      userAgent: "*",
      allow: "/",
      disallow: ["/admin/", "/myprofile/", "/chat", "/payment/", "/auth/", "/api/"],
    },
    sitemap: `${BASE}/sitemap.xml`,
  };
}
```

추가로 인증 전용 페이지에는 `robots: { index: false }`를 줘서 색인에서 확실히 빼 줍니다(가이드 8장).

```tsx
// 예: myprofile 레이아웃 또는 각 page.tsx
export const metadata = { title: "마이페이지", robots: { index: false, follow: false } };
```

### 확인 (가이드 10장)

dev 서버를 띄우고 `curl`로 **서버 원문**을 봅니다. 화면이 아니라 원문이어야 합니다.

```bash
npm run dev
curl -s http://localhost:3000/petsitters | grep -i '<h1'          # 시터 이름이 보이면 SSR 통과
curl -s http://localhost:3000/petsitters/1 | grep -iE '<title>|canonical'
curl -s http://localhost:3000/sitemap.xml | head
curl -s http://localhost:3000/robots.txt
```

`<h1>`에 데이터가 안 보이고 "로딩 중"만 보이면 아직 클라이언트 렌더링이라는 뜻이니 2장으로 돌아갑니다.

## 5. `notifications` RLS 정책 확인

`NotificationToaster`의 코드는 문제 없습니다. 다만 클라이언트 필터 `user_id=eq.${userId}`는 보안 장치가 아니라, 실제 보안은 DB의 RLS 정책에 달려 있습니다. 정책이 실제로 걸려 있는지 이렇게 확인하세요.

```sql
-- Supabase SQL Editor에서
select relrowsecurity from pg_class where relname = 'notifications';   -- t 여야 함(RLS ON)
select policyname, cmd, qual from pg_policies where tablename = 'notifications';
```

`SELECT` 정책에 `auth.uid() = user_id` 조건이 보이면 안전합니다. 없거나 RLS가 꺼져 있으면 마이그레이션에 이걸 추가해 주세요.

```sql
alter table notifications enable row level security;

create policy "본인 알림만 조회"
  on notifications for select
  using (auth.uid() = user_id);
```

이렇게 해 두면 클라이언트가 필터를 어떻게 바꿔도 DB가 남의 알림 행을 아예 안 내려줍니다. 그게 진짜 방어선입니다.
