## 1. 결제 금액 — 왜 "서버가 계산한 값만 믿기"가 정답인가

이번에 고친 방향이 정확히 이겁니다. 원리를 한 번 더 정리해 둘게요.

결제에서 클라이언트가 보내는 금액은 **절대 신뢰하면 안 되는 값**입니다. 브라우저 개발자도구나 URL 한 줄로 얼마든지 바꿀 수 있기 때문인데요, 그래서 과거의 `createPayment(id, method, requestedAmount)`처럼 클라가 보낸 금액을 받아 저장하는 구조는 `?amount=1`로 1원 결제가 뚫렸던 겁니다.

지금 코드는 이렇게 바뀌었습니다.

```ts
// actions/payments.ts — 클라 금액 인자가 아예 없음
export async function createPayment(
  reservationId: string,
  payMethod: "CARD" | "VIRTUAL_ACCOUNT" | "TRANSFER",
) {
  // ...
  const amount = reservation.total_price; // 서버가 계산해 저장한 값만 사용
  if (amount < 1000) return { error: { code: "VALIDATION_ERROR", ... } };
  // 이 amount로 payments 행 생성 + 포트원 요청
}
```

여기에 결제 확정 단계에서 포트원에 실제 결제액을 되물어 한 번 더 대조하는 이중 방어까지 있습니다.

```ts
// verifyAndConfirmPayment
const portonePayment = await portoneRes.json();
const paidAmount = portonePayment?.amount?.total;
if (paidAmount !== payment.amount) {
  return { error: { code: "AMOUNT_MISMATCH", ... } };
}
```

**남은 마무리 한 줄** — `payment/page.tsx`에서 화면에 보여주는 금액도 서버값으로 맞추기. 지금은 URL 쿼리의 `amount`를 표시용으로 쓰는데, 실제 청구는 서버값이라 안전하지만 사용자가 URL을 손대면 "확인 화면엔 1원, 실제 청구는 3만원"처럼 보일 수 있습니다. 확인 모달을 열 때 먼저 `createPayment` 결과를 받아 그 `amount`로 그려주면 표시와 청구가 항상 일치합니다.

## 2. 공개 데이터에서 개인정보 빼기 — 지금 방식이 맞고, `reviews`만 남았습니다

펫시터 목록 RPC는 이미 잘 정리됐습니다. 실명·인증 UUID·전체주소를 빼고 표시명·구동 지역·뭉갠 좌표만 내려주는 방향이 정답입니다. 같은 원리를 아직 안 적용한 곳이 후기(`reviews`) 테이블입니다.

지금 상태 (실측):

```bash
# 로그인 없이 호출해도 작성자 UUID가 그대로 나옴
GET /rest/v1/reviews?select=*
# → [{ "owner_id": "74cf5cab-...", "sitter_id": "6378...", "content": "...", ... }]
```

후기 본문·별점·이미지는 공개가 맞지만, `owner_id`(누가 썼는지의 인증 UUID)는 나갈 이유가 없습니다. 해결은 두 가지 중 하나입니다.

**방법 A — 공개용 RPC/뷰로 필요한 필드만 내려주기** (펫시터 목록과 같은 패턴, 권장)

```sql
create or replace function get_sitter_reviews(p_sitter_id uuid)
returns table (
  id uuid,
  rating int,
  content text,
  image_urls text[],
  reviewer_name text,   -- users.full_name 대신 표시명
  created_at timestamptz
)
language sql stable security definer set search_path = public as $$
  select r.id, r.rating, r.content, r.image_urls,
         u.full_name as reviewer_name, r.created_at
  from reviews r join users u on u.id = r.owner_id
  where r.sitter_id = p_sitter_id
  order by r.created_at desc;
$$;
```

이러면 `owner_id`·`sitter_id` UUID가 응답에서 사라집니다. 앱은 `supabase.rpc("get_sitter_reviews", { p_sitter_id })`로 바꿔 부르면 됩니다.

**방법 B — reviews 테이블 직접 SELECT를 RLS로 막고, 앱은 위 RPC만 쓰게** 하기. anon에 대한 `select` 정책을 없애면 테이블 직접 조회가 0행이 되고, 공개 데이터는 RPC 경로로만 나갑니다.

발표 블로커는 아니니, 내일 발표를 먼저 끝내고 공개 레포로 올리기 전에 처리하면 됩니다.

## 3. 자기 예약 차단 — 두 진입점 모두 막은 게 핵심

이미 이렇게 되어 있습니다. 왜 "두 곳 다"가 중요한지만 짚을게요.

```ts
// createReservation, createPetsitterReservationRequest 양쪽 동일
const sitterUserId = (service.sitters as { user_id: string }).user_id;
if (sitterUserId === user.id) {
  return { error: { code: "FORBIDDEN", message: "본인에게는 예약할 수 없습니다." } };
}
```

예약을 만드는 서버 액션이 두 개(일반 예약 / 게시글 기반 요청)라, 한쪽만 막으면 다른 경로로 우회됩니다. 둘 다 막았으니 완결입니다. UI의 `isSelf` 버튼 숨김은 사용자 편의고, 실제 방어선은 이 서버 가드라는 점만 기억해 두면 됩니다.

## 4. 발표 전 셀프 체크 2가지 (5분)

1. **결제 흐름**: 시터 계정과 보호자 계정을 나눠, 보호자로 예약 → 시터가 수락 → 보호자가 결제까지 태워보고, 최종 결제창 금액이 예약 금액과 같은지 눈으로 확인.
2. **비로그인 노출**: 시크릿 창(로그인 X)으로 펫시터 목록을 열어, 보이는 정보가 이름·대략 지역·평점까지인지 확인. (개발자도구 Network 탭에서 목록 응답을 열어 `user_id`가 없으면 통과.)
