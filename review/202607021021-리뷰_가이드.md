## 2. [필수] `/terms` 500 — 함수 prop 제거

`LegalPage`가 `"use client"`이다 보니, 서버 컴포넌트인 `terms/page.tsx`에서 함수(`renderItemText`)를 넘길 수 없습니다. 두 가지 중 하나로 풀면 됩니다.

### 방법 A (추천): 링크 파싱을 LegalPage 안에서 처리

지금 `renderItemText`가 하는 일이라곤 "`[개인정보처리방침]` 같은 토큰을 Link로 바꾸는" 게 전부입니다. 이 로직을 `LegalPage`(클라 컴포넌트) 안으로 옮기고, 페이지에서는 **함수 대신 데이터**만 넘겨 주세요.

```ts
// terms/page.tsx — 함수 대신 링크 매핑(직렬화 가능한 데이터)만 전달
<LegalPage
  title="이용약관"
  articles={ARTICLES}
  linkMap={{ 개인정보처리방침: "/privacy" }}   // ← 객체(직렬화 OK)
/>
```

```tsx
// LegalPage.tsx (use client) 내부에서 렌더 시 파싱
function renderItemText(text: string, linkMap: Record<string, string>) {
  const m = text.match(/^([\s\S]*?)\[([^\]]+)\]([\s\S]*)$/);
  if (m && linkMap[m[2]]) {
    return (<>{m[1]}<Link href={linkMap[m[2]]} className="...">{m[2]}</Link>{m[3]}</>);
  }
  return text;
}
// items.map(item => <li>{renderItemText(item, linkMap)}</li>)
```

### 방법 B: terms 페이지를 클라 컴포넌트로

`terms/page.tsx` 맨 위에 `"use client"`를 붙이면 함수 전달 제약은 사라집니다. 다만 이렇게 하면 약관 페이지가 CSR로 바뀌어 SEO에 불리하니, **방법 A를 권합니다**(약관은 정적 콘텐츠라 서버 렌더가 맞습니다).

## 3. [필수] 1원 결제 — `createPayment` 서버 재계산

핵심은 **클라가 준 금액을 저장하는 게 아니라, 서버가 예약 실제가를 계산해서 그 값으로 결제**하게 만드는 것입니다.

```ts
// payments.ts — createPayment
export async function createPayment(reservationId: string, payMethod: string) {
  // 1) 예약을 서버에서 조회
  const { data: reservation } = await supabase
    .from("reservations")
    .select("id, owner_id, service_id, total_price, status")
    .eq("id", reservationId)
    .single();
  if (!reservation) throw new Error("예약을 찾을 수 없습니다");

  // 2) 서버가 실제 결제금액 재계산 (서비스가 + 승인된 추가금 합)
  const { data: service } = await supabase
    .from("services").select("price").eq("id", reservation.service_id).single();
  const { data: extras } = await supabase
    .from("extra_charges").select("amount").eq("reservation_id", reservationId).eq("status", "approved");
  const serverAmount = (service?.price ?? 0) + (extras ?? []).reduce((s, e) => s + e.amount, 0);

  // 3) requestedAmount 인자 자체를 없애고 serverAmount 로만 결제
  const { data: payment } = await supabase.from("payments").insert({
    reservation_id: reservationId,
    amount: serverAmount,       // ← 클라값이 아니라 서버 계산값
    pay_method: payMethod,
    status: "ready",
  }).select().single();

  return payment; // 이후 포트원에 serverAmount 로 결제 요청
}
```

`ChatClient.tsx:556`의 호출부에서는 세 번째 인자(`totalAmount`)를 빼고 `createPayment(reservationId, "CARD")`로 부르면 됩니다. 화면에 보여 줄 금액은 따로 계산해 표시하되, **결제에 쓰는 금액만큼은 서버 값**을 쓰는 게 원칙입니다. 웹훅의 대조(`paidAmount === payment.amount`)는 그대로 둬도, 이제 `payment.amount`가 서버 실제가라서 1원 결제는 성립하지 않습니다.

## 5. [필수] 공개 RPC PII 축소

`get_petsitters_filtered`는 지도/목록용인데 실명·auth user_id·전체주소까지 내보내고 있습니다. 지도에는 이런 것들이 필요 없거든요.

```sql
-- RPC 반환 컬럼에서 제거: full_name, user_id, available_area(전체주소)
-- 남길 것: id(시터 id), display_area(구·동 단위), fuzz 좌표, base_price, rating, service_types
create or replace function get_petsitters_filtered(...)
returns table (
  id uuid,
  display_area text,          -- "광주 북구" 수준
  latitude double precision,  -- 이미 fuzz된 값
  longitude double precision,
  base_price int,
  rating numeric,
  service_types text[]
) ...
```

상세 페이지에서 실명이 필요하다면, 그건 로그인·예약 맥락에서 따로 조회(RLS로 보호된 경로)해서 가져오면 됩니다. 목록/지도 단계에서 실명과 user_id가 익명 사용자에게 나갈 이유는 없으니까요.

## 6. [제안] Supabase 클라이언트 하나로

`src/lib/supabase.ts`와 `src/utils/supabase/client.ts`가 각각 브라우저 클라이언트를 만들다 보니 "Multiple GoTrueClient instances" 경고가 납니다. 클라 컴포넌트에서 쓰는 브라우저 클라이언트는 한 곳에서만 만들어(모듈 스코프 싱글턴) 돌려쓰도록 정리해 주면, 경고도 사라지고 세션 저장소 충돌 위험도 줄어듭니다.
