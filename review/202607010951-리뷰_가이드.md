## 1. [필수·중대] 결제 금액 서버 검증

원칙은 하나입니다 — **금액은 클라이언트가 정하지 않고, 서버가 예약에서 계산한 뒤 PortOne이 실제로 승인한 금액과 대조한다.** 손볼 곳은 세 군데입니다.

### (1) `actions/payments.ts` — 예약 금액을 강제

```ts
// createPayment (지금: const amount = requestedAmount ?? reservation.total_price)
const { data: reservation } = await supabase
  .from("reservations")
  .select("id, total_price, user_id, sitter_id")
  .eq("id", reservationId)
  .single();

if (!reservation) return { error: "예약 없음" };

// 1차 결제는 클라가 보낸 requestedAmount를 믿지 말고 예약 실금액으로 강제
const amount = reservation.total_price;
// (추가금 결제가 별도로 있다면, 그 항목도 서버 테이블에서 조회한 값으로만)

await supabase.from("payments").insert({
  reservation_id: reservationId,
  amount,                 // ← 서버 값
  status: "pending",      // 승인 전까지 pending
});
```

### (2) `api/portone/webhook/route.ts` — 실제 승인액과 대조

```ts
if (event.type === "Transaction.Paid") {
  const paymentId = event.data.paymentId;

  // PortOne에 실제 결제 내역을 물어본다
  const res = await fetch(`https://api.portone.io/payments/${paymentId}`, {
    headers: { Authorization: `PortOne ${process.env.PORTONE_API_SECRET}` },
  });
  const paid = await res.json();
  const paidAmount = paid.amount.total;

  // 우리 DB의 예약/결제 금액과 대조
  const { data: payment } = await supabase
    .from("payments")
    .select("id, amount, reservation:reservations(total_price)")
    .eq("portone_payment_id", paymentId)
    .single();

  if (!payment || paidAmount !== payment.amount) {
    // 금액 불일치 → paid로 만들지 말고 로그 남기고 보류/취소
    console.error("결제 금액 불일치", { paidAmount, expected: payment?.amount });
    return new Response("amount mismatch", { status: 400 });
  }

  // 일치할 때만 확정
  await supabase.from("payments").update({ status: "paid" }).eq("id", payment.id);
}
```

## 2. [필수] 프로덕션 빌드 복구 (tsc 8건)

### 유형 A — `.update()` 페이로드 타입 (admin.ts:205, pets.ts:194, services.ts:125, sitters.ts:154/200/309)

`Record<string, ...>`나 `Partial<>`를 `.update()`에 그대로 넘기면 Supabase 생성 타입의 `never` 인덱스와 부딪힙니다. 넘기는 객체에 테이블 타입을 붙여 좁혀 주세요.

```ts
import type { TablesUpdate } from "@/types/database"; // 생성 타입 경로에 맞게

// 지금: const updates: Record<string, string | null> = {...}
const updates = {
  status,
  memo,
} satisfies TablesUpdate<"reservations">;   // ← 테이블명 맞게

await supabase.from("reservations").update(updates).eq("id", id);
```

`satisfies`를 쓰면 컬럼 오타나 없는 필드가 그 자리에서 걸리는 동시에 `.update()`가 받아들이는 타입이 됩니다.

### 유형 B — 조인 select에 `id` 누락 (admin/page.tsx:13, state/page.tsx:6)

`sitter.users`를 `UserInfo`로 쓰면서 select에 `id`를 빠뜨려 shape이 어긋난 경우입니다.

```ts
// 지금: .select("*, users(full_name, display_area)")
.select("*, users(id, full_name, display_area)")  // ← id 추가
```

### 근본 처방 — RPC를 생성 타입에 포함

`as any`/`as unknown as`가 73건이나 되는 이유는 생성 타입에 RPC 시그니처가 없어서인데, 아래 명령으로 타입을 다시 뽑으면 캐스팅과 빌드 에러가 같이 줄어듭니다.

```bash
npx supabase gen types typescript --project-id <프로젝트id> --schema public > src/types/database.ts
```

그러면 `supabase.rpc("get_petsitters_filtered", {...})`의 인자·반환 타입이 잡혀서 RPC 호출부의 `as any`를 걷어낼 수 있습니다.

### 확인
```bash

npm run build      # "Failed to type check" 안 뜨면 성공
```

`actions/reservations.ts`의 `createReservation`에 두 줄짜리 가드를 추가합니다.

const { data: sitter } = await supabase
  .from("sitters").select("id, user_id").eq("id", sitterId).single();

// (1) 자기 자신 예약 차단
if (sitter?.user_id === user.id) {
  return { error: "본인에게는 예약할 수 없습니다." };

const { data: myPets } = await supabase

## 4. [필수] 공개 펫시터 RPC PII 최소화

`get_petsitters_filtered` RPC를 손봐 반환 컬럼을 줄입니다. 화면에서는 `display_area`만 쓰니까요.

```sql
create or replace function get_petsitters_filtered(...)
returns table (
  id uuid,
  display_name text,        -- full_name 대신 표시명
  display_area text,        -- "북구 두암동"
  approx_lat numeric,       -- round(latitude, 2) — 대략 좌표
  approx_lng numeric,
  hourly_rate int,
  rating numeric
)
security definer
as $$
  select s.id, s.display_name, s.display_area,
         round(s.latitude, 2), round(s.longitude, 2),
         s.hourly_rate, s.rating
  from sitters s
  where ...
$$ language sql;
```

핵심은 `user_id`(auth UUID)와 `full_name`(실명), 정확 좌표를 빼는 것입니다. 실명이나 정확한 위치가 필요한 상세 화면은 인증 사용자만 들어오니, 거기서 따로 조회하면 됩니다.

그리고 `api/sitters/route.ts`는 지금 존재하지 않는 RPC를 불러 상시 500이 나는 데다 아무도 쓰지 않으니 **파일을 삭제**하세요(나중에 되살아나면 무인증 PII 라우트가 되어 버립니다).

## 5. [필수] 채팅 상대 메시지 이중 수신

수신 경로를 하나로 합칩니다. broadcast에 발신자 프로필과 payment_data가 실려 온다면 broadcast만 남기고 postgres_changes 구독은 지우면 됩니다(반대여도 상관없습니다).

```ts
// useChatMessages.ts — 두 구독 중 하나만
channel.on("broadcast", { event: "new-message" }, ({ payload }) => {
  addMessageDedup(payload);   // 아래 공유 dedup
});
// channel.on("postgres_changes", ...) ← 제거

// 중복 제거를 스냅샷이 아니라 공유 ref로
const seenIds = useRef<Set<string>>(new Set());
function addMessageDedup(msg) {
  if (seenIds.current.has(msg.id)) return;
  seenIds.current.add(msg.id);
  setMessages((prev) => [...prev, msg]);
}
```

`setMessages(prev => prev.some(...))` 가드는 두 이벤트가 같은 스냅샷을 보는 순간 사이로 새 버리니, 판단 기준을 state 스냅샷이 아니라 `useRef`의 `Set`으로 옮기는 게 핵심입니다.
