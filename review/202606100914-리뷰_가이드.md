## 1. 빌드 복구 — 타입 에러 5곳 (`[필수]`)

`npm run build` 가 타입 체크에서 멈춰 배포가 안 되는 상태입니다. 먼저 닫읍시다.

### 1-1. MapMarker `id` — `src/app/petsitters/[id]/page.tsx:352`

`KakaoMap`의 `MapMarker` 가 `id: number` 를 필수로 받습니다. 한 줄입니다.

```tsx
// Before
markers={[{ lat: PETSITTER.lat, lng: PETSITTER.lng }]}
// After
markers={[{ id: PETSITTER.id ?? 0, lat: PETSITTER.lat, lng: PETSITTER.lng }]}
```

### 1-2. 조인 결과 캐스팅 4곳 — `applications.ts` / `payments.ts` / `api/sitters/[id]/route.ts`

문제 코드 모양:

```ts
const { data: application } = await db
  .from("applications")
  .select(`..., requests!inner(id, owner_id, ...)`)
  .single();

const requestRow = application.requests as { id: string; ... };  // [X] TS2352
```

**왜 막히나**: supabase-js는 `requests!inner(...)` 조인을 **배열** 로 추론합니다. 배열을 단일 객체로 `as` 단언하면 "서로 안 맞는다"며 거부합니다. 런타임엔 `!inner` 가 1:1이라 객체로 오지만, 타입은 그걸 모릅니다.

**임시(지금 당장 빌드 통과)**: `as unknown as {...}` 로 한 단계 우회.

```ts
const requestRow = application.requests as unknown as { id: string; owner_id: string; ... };
```

**정석(권장, 나중에)**: Supabase가 만들어주는 DB 타입을 쓰면 `as` 자체가 사라집니다.

```bash
npx supabase gen types typescript --project-id <PROJECT_ID> > src/types/database.ts
```

```ts
import { createServerClient } from "@supabase/ssr";
import type { Database } from "@/types/database";
// createClient 들에 <Database> 제네릭을 붙이면 select 결과 타입이 정확해집니다.
```

> 4곳 다 같은 패턴입니다: `payments.ts:82`(`sitters!inner(users!inner(full_name))`), `payments.ts:109`(`reservations!inner(...)`), `api/sitters/[id]/route.ts:34`(`sitter.users`). 우선 `as unknown as` 로 막고, 시간 날 때 gen types로 정리하길 권합니다.

고친 뒤 **반드시** 다시 확인:

```bash
npx tsc --noEmit && npm run build
```

## 2. 인증 마무리 — 로그아웃 · 회원탈퇴 · 보호 라우트 (`[필수]`/`[제안]`)

### 2-1. 회원탈퇴를 실제로 동작하게 (`[필수]`)

지금 `withdraw/page.tsx` 의 `handleDelete` 는 화면만 "완료"로 바꿉니다. gyuhwa가 만든 `deleteUser()` 액션을 붙이면 됩니다.

```tsx
"use client";
import { deleteUser } from "@/app/actions/users";
import { createClient } from "@/utils/supabase/client";

const handleDelete = async () => {
  const res = await deleteUser();
  if (res.error) {
    alert(res.error.message);   // 진행 중 예약이 있으면 여기서 막힘
    return;
  }
  await createClient().auth.signOut();  // 세션 종료
  setShowModal(false);
  setDone(true);
};
```

**짚어둘 점**: 현재 `deleteUser()` 는 `users` 테이블에 `deleted_at` 만 찍는 **소프트 삭제** 입니다. Supabase Auth의 실제 계정(`auth.users`)은 남아 있어, 같은 소셜 계정으로 다시 로그인하면 콜백에서 되살아날 수 있습니다. "복구 불가" 문구와 맞추려면 둘 중 하나를 팀에서 정하세요.

- (A) 소프트 삭제 유지 + OAuth 콜백에서 `deleted_at IS NOT NULL` 이면 로그인 거부.
- (B) service-role로 실제 삭제:
  ```ts
  // actions/users.ts (deleteUser 안, deleted_at 처리 뒤)
  const admin = createServiceClient();
  await admin.auth.admin.deleteUser(user.id);
  ```
  단 (B)는 예약/결제 이력 정합성(FK)을 먼저 정리해야 합니다.

### 2-2. 로그아웃에 signOut 붙이기 (`[제안]`, 2차 미해결)

`myprofile/page.tsx` 의 로그아웃 버튼 2곳(데스크탑 401줄·모바일 543줄)을 같은 패턴으로.

```tsx
import { createClient } from "@/utils/supabase/client";

const handleLogout = async () => {
  await createClient().auth.signOut();
  router.push("/auth/login");
};
// onClick={handleLogout}
```

지금처럼 `router.push` 만 하면 **쿠키 세션이 살아 있어**, 주소창에 `/myprofile` 을 다시 치면 그대로 들어가집니다. `signOut()` 이 세션 쿠키를 지워줍니다.

### 2-3. 루트 `middleware.ts` 추가 (`[필수]`, 1·2차 미해결)

`utils/supabase/middleware.ts`(헬퍼)는 있는데, Next가 실행하는 **루트 `middleware.ts`** 가 없어 한 번도 안 돌고 있습니다. 프로젝트 루트(또는 `src/`)에 만들어 헬퍼를 연결하세요.

```ts
// middleware.ts (프로젝트 루트)
import { type NextRequest } from "next/server";
import { updateSession } from "@/utils/supabase/middleware";

export async function middleware(request: NextRequest) {
  return await updateSession(request);
}

export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico|.*\\.(?:svg|png|jpg|jpeg|gif|webp)$).*)"],
};
```

이걸 붙여야 (1) 세션이 매 요청 갱신되고, (2) `/myprofile` 같은 보호 라우트를 비로그인 시 `/auth/login` 으로 돌려보낼 수 있습니다.

## 3. 결제 확정 검증 (`[제안]`)

`createPayment` 는 결제 "준비(ready)"까지만 만듭니다. PortOne 결제창이 성공한 뒤, **클라이언트 말만 믿지 말고** 서버에서 PortOne에 실제 결제를 재조회해 금액이 맞는지 확인하고 `paid` 로 바꿔야 합니다.

```ts
// actions/payments.ts 에 추가 (혹은 /api/payments/webhook)
export async function confirmPayment(paymentId: string) {
  const res = await fetch(`https://api.portone.io/payments/${paymentId}`, {
    headers: { Authorization: `PortOne ${process.env.PORTONE_API_SECRET}` },
    cache: "no-store",
  });
  const pay = await res.json();
  // pay.amount.total 이 우리 DB의 amount와 같은지 검증 후에만 status='paid'
}
```

명세서 "11. PortOne 웹훅"에 계획이 있으니, 이 검증을 빼먹지 않도록 같이 챙기세요.

## 4. RLS 공개 정책 방향 정하기 (`[제안]`)

지금 `sitters` 가 anon에 `[]`(0행)이라, 비로그인 유저가 클라이언트에서 직접 조회하면 빈 목록입니다. 두 길이 있습니다.

- (A) **지금처럼 서버 라우트(`/api/sitters`, service client) 경유** — anon 키로는 아무것도 못 읽으니 더 안전. 대신 모든 공개 조회를 API로 짜야 함. (현재 방식)
- (B) **활성 시터만 공개 SELECT 정책으로 열기**:
  ```sql
  create policy "active sitters are public"
    on public.sitters for select
    using (status = 'active');
  ```
  클라이언트에서 직접 조회 가능. 대신 어떤 컬럼까지 열지 주의(전화번호 등 민감 컬럼 분리).

정답은 없습니다. 팀이 "공개 데이터 조회를 API로 통일할지, RLS로 열지" 한 번 합의해두면 이후가 깔끔합니다.
