## 1. [필수] 채팅 메시지가 두 번 보이는 문제

지금은 메시지가 화면에 들어오는 경로가 둘입니다.
- 보낼 때: `handleSend` 성공 → `addMessage(result.data)` (낙관적 추가)
- 동시에: realtime INSERT 구독이 같은 행을 또 추가

양쪽 다 id 검사 없이 `[...prev, msg]`로 밀어 넣다 보니 본인 메시지가 두 번 보입니다. 메시지의 진실 소스를 하나로 모으면 해결됩니다.

### 권장 (A) realtime 한 경로만 신뢰 — 가장 단순
```ts
// chat/page.tsx — 전송 성공 후 직접 append 하지 않는다
const handleSend = async () => {
  if (!input.trim() || sending) return;
  setSending(true);
  try {
    await sendMessage(activeRoomId, input); // 저장만. 화면 추가는 realtime이 담당
    setInput("");
  } finally {
    setSending(false);
  }
};
// useChatMessages 의 realtime INSERT 구독이 새 메시지를 화면에 넣는다(이미 구현돼 있음)
```
이러면 내 메시지도 realtime을 거쳐 한 번만 들어옵니다. 상대 메시지와 경로가 같아 일관적입니다.

### (B) 즉시성을 원하면: 낙관 추가 + id 중복 가드
전송하자마자 보여주고 싶다면 임시 id로 낙관 추가를 하고, realtime이 도착하면 교체하거나 중복을 거르면 됩니다.
```ts
// 양쪽 append 지점 모두 id 중복 가드
setMessages((prev) =>
  prev.some((m) => m.id === msg.id) ? prev : [...prev, msg]
);
```

> 그 전에 Supabase 대시보드에서 messages 테이블의 Realtime(Replication)이 켜져 있는지 확인하세요. 꺼져 있으면 상대 메시지가 안 들어옵니다. 이게 실시간 채팅의 전제입니다.

## 2. [제안] UserProvider의 users 직접 SELECT

`UserProvider`가 클라이언트에서 `users`를 직접 조회합니다. 본인 행을 읽는 거라 RLS 정책이 있어야 동작합니다.

```sql
-- 로그인 사용자가 자기 행만 읽도록 (없으면 추가)
create policy "users can read own row"
on users for select
to authenticated
using (auth.uid() = id);   -- id 컬럼이 auth.uid()와 매핑되는 구조에 맞게
```
정책이 없으면 `data`가 null이 되고, 로그인을 했는데도 헤더가 비로그인 상태로 보입니다. 한 단계 더 간다면 프로필을 서버 컴포넌트에서 내려주거나 `/api/me`를 거치게 해서, UI가 DB 스키마에 직접 묶이지 않게 하는 방법도 있습니다.

그리고 `userStore.verifyUser`가 정의만 되고 안 쓰이고 있습니다. verification 성공 시 호출하도록 연결하거나, 주석으로 의도를 남겨주세요.

## 3. [필수] 회원탈퇴 실연결 (5·6차 이월)

`myprofile/settings/withdraw/page.tsx`의 `handleDelete`가 모달만 닫고 끝나 있습니다. 실제 탈퇴 흐름을 연결하세요.

```ts
const handleDelete = async () => {
  try {
    const res = await fetch("/api/user/withdraw", { method: "DELETE" });
    if (!res.ok) throw new Error("탈퇴 실패");
    await supabase.auth.signOut();   // 세션 정리
    clearUser();                      // userStore 초기화
    router.replace("/");              // 메인으로
  } catch (e) {
    // 사용자에게 실패 안내
  }
};
```
서버 라우트에서는 `supabaseAdmin.auth.admin.deleteUser(userId)`로 처리하거나, 소프트 딜리트 정책에 맞춰 처리합니다. 어느 쪽이든 계정이 실제로 사라지는지(또는 비활성화되는지)는 한 번 확인해 주세요.
