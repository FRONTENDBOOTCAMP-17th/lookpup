### 결제 흐름 — 한쪽은 좋아졌는데, 다른 쪽이 무너졌습니다

먼저 칭찬부터 하겠습니다. 예약(book) 플로우는 `createReservation` 서버액션을 거치도록 정리돼서, 결제 금액이 더 이상 클라이언트 입력에서 오지 않고 **DB의 `service.price`에서 도출**됩니다(`actions/reservations.ts:178~211`, `total_price: service.price`). 금액의 진실을 서버가 쥐고 있다는 점에서 방향이 정확합니다.

문제는 두 군데입니다.

**(1) `/payment` standalone 페이지가 그대로 남아 있습니다.** `src/app/payment/page.tsx:57`을 보면 아직도

```ts
const amount = Number(searchParams.get("amount") ?? 35000);
const feeRate = Number(searchParams.get("fee") ?? 0.05);
```

URL 쿼리에서 금액을 그대로 받고, `handlePay`(80~)는 `createPayment`를 거치지 않고 `requestPayment`로 바로 PortOne을 호출합니다. 즉 `payments` 행이 생성되지 않은 채 결제만 일어납니다. 고객 정보도 `"테스트"/"010-0000-0000"/"test@test.com"`(90~92) 더미 그대로입니다.

**(2) 웹훅의 금액 검증 코드가 삭제됐습니다.** 이게 이번 회차에서 가장 신경 쓰이는 부분입니다. 14차 때는 `portone/webhook/route.ts`에 PortOne API로 조회한 결제금액과 `payments.amount`를 대조하는 로직이 들어 있었는데, 커밋 `49d8d0a`에서 그게 빠졌습니다. 지금 웹훅은(`route.ts:35~63`) **HMAC 서명만 확인**하고, 서명이 맞으면 `payment_id`로 행을 찾아 바로 `status: "paid"`로 올립니다. 서명은 "이 요청이 PortOne에서 왔다"만 보장할 뿐, **얼마가 결제됐는지는 검증하지 않습니다.**

두 개가 겹치면 `/payment?amount=1`로 1원 결제를 만들어도 웹훅이 금액을 안 보니 그대로 통과시킵니다. 14차에서 한 번 막았던 구멍이 다시 열린 셈이라, 이번 [필수]의 1번으로 올립니다.

### SEO — 14차와 동일

`board`·`board/[id]`·`petsitters`·`petsitters/[id]` 네 페이지 모두 첫 줄이 `"use client"`입니다. `sitemap.ts`·`robots.ts`는 파일 자체가 없고, `layout.tsx`에 `metadataBase`도, 상세 페이지에 `generateMetadata`도 없습니다. 마감 전 최소 구성으로라도 넣어두자고 다시 권합니다(가이드 참고).

### 채팅 reservationId 폴백 — 부분

`chat/page.tsx`의 reservationId 폴백(`getAcceptedReservationBySitter` 최근 1건)이 아직 남아 있습니다. 다만 `createPayment` 내부의 owner_id 체크가 최소한의 방어는 해주고 있어, 우선순위는 결제 [필수] 두 건 다음으로 둡니다.

## 3. 이번 새 [필수]

**1. [필수/보안] 웹훅 금액 검증 복원 + `/payment` 정리**
`portone/webhook/route.ts:71~88` 결제 처리부에 금액 대조가 없습니다. `49d8d0a`에서 빠진 검증을 복원하거나, 더 확실하게 PortOne 결제 단건조회 API로 `status === "PAID"`와 금액을 `payments.amount`와 대조한 뒤에 `paid`로 올리세요. 그리고 `/payment/page.tsx`는 `createPayment`를 거치지 않으니 **삭제하거나 비활성화**하는 게 맞습니다.

**2. [필수/보안] `createReservation` 자기예약 서버 차단**
`actions/reservations.ts:137~` 에 시터 본인이 자기 자신을 예약하는 걸 막는 가드가 없습니다. UI(`petsitters/[id]/page.tsx:118` `isSelf`)에서만 버튼을 숨기고 있어서, API/URL로 직접 호출하면 자기예약이 통과됩니다. 서버액션에서 `sitter.user_id === user.id`(또는 service 소유자 == 호출자)면 거절하도록 가드를 추가하세요.

- `api/sitters/[id]/route.ts:47-48` — **정확한 위경도(latitude/longitude)** 가 인증 없이 공개됩니다. 시터의 집 좌표가 그대로 노출될 수 있으니, 구/동 단위로 fuzzing 하거나 `display_area`(표시용 지역명)만 내보내는 쪽을 권합니다.

## 6. 팀 공통

이번 회차에서 반복해서 드러난 한 가지를 짚겠습니다. **UI에서 막아도 서버액션/API에 같은 검증이 없으면 우회됩니다.** 자기예약(UI `isSelf`만)과 결제 금액(`/payment` URL 쿼리)이 딱 그 패턴이었습니다. 버튼을 숨겼다고 막은 게 아니라, 그 동작을 실제로 수행하는 서버 코드에 검증이 있어야 막은 거라 보면 됩니다. 앞으로 새 기능을 붙일 때 "이 검증, 서버에도 있나?"를 한 번씩 자문해보면 좋겠습니다.

SEO 기본(metadataBase·sitemap·robots·generateMetadata)은 마감 전 최소 구성만이라도 넣읍시다. 공개 페이지가 CSR 일색이라 크롤러엔 빈 화면으로 보이는 상태입니다.

### Top 3 (16차 대조용)
1. [필수/보안] 웹훅 결제 금액검증 복원 + `/payment` 제거
2. [필수/보안] `createReservation` 자기예약 서버 차단
3. [필수] `notifications` RLS 실재 확인
