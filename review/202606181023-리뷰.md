## 2. 채팅 메시지 중복 해결 — 잘 고쳤습니다 [칭찬]

7차에는 전송 시 `addMessage`(로컬 추가)와 Realtime INSERT 구독이 둘 다 본인 메시지를 push 하는 바람에 화면에 두 번 보였습니다.
이번엔 실시간 수신을 broadcast로 바꾸면서 이렇게 정리됐네요(`useChatMessages.ts`).

```ts
// 수신: broadcast 구독 — 본인이 보낸 건 무시(전송 시 이미 로컬에 추가했으므로)
.on("broadcast", { event: "new_message" }, ({ payload }) => {
  const m = payload as MessageApiItem;
  if (m.sender_id === userId) return;   // ← 본인 메시지 중복 차단
  setMessages((prev) => [...prev, { id: m.id, from: "other", ... }]);
})
```

"전송자는 로컬에 한 번, 수신자는 broadcast로 한 번"이라는 단일 소스가 생겼습니다. 7차에 단일 소스로 모으자고 했던 방향 그대로라
보기 좋았습니다. 비동기 실시간은 초보 단계에서 중복·누락이 가장 흔하게 터지는 곳인데, 원인을 정확히 짚어 고친 점을 칭찬하고 싶습니다.

> 다만 이번엔 OAuth 2계정 + Realtime 동시 연결이 필요해 강사 환경에서 두 사람 간 실제 송수신까지는 자동으로 돌리지 못했습니다(코드로 확인).
> 한 가지만 덧붙이면, broadcast는 전송 성공 여부와 별개로 휘발성이라 상대가 그 순간 접속 중이 아니면 그 메시지를 놓칩니다.
> 다행히 방에 다시 들어올 때 DB 조회(`setMessages(mapped)`)로 복원되니 큰 문제는 아닙니다. 다만 이 구조를 미리 알아두면 나중에 안 읽은 메시지 처리할 때 도움이 됩니다.

## 3. 이번 1순위 — 회원탈퇴 실제 연결 [필수·이월]

`myprofile/settings/withdraw/page.tsx`를 보면 탈퇴 확인 모달까지는 잘 만들어져 있는데, 정작 확인을 눌렀을 때 하는 일이 화면 상태만 바꾸는 것입니다.

```tsx
const handleDelete = () => {
  // 실제 deleteUser() 호출도, signOut 도 없음
  setDone(true);   // 66행 — "완료" 화면만 보여줌
};
```

사용자는 "탈퇴 완료" 화면을 보는데 계정은 그대로 남아 있는 상태죠. `deleteUser()` 액션은 이미 만들어 두셨으니 연결만 하면 됩니다.
탈퇴는 되돌릴 수 없는 동작이라 호출 → 성공 확인 → 로그아웃 → 안내 순서로 묶어 두는 편이 안전합니다. 구체적인 코드는 가이드에 적어 두었습니다.
여러 회차 이어진 항목이다 보니, 혹시 탈퇴 시 함께 지워야 할 데이터(예약·결제 이력 등) 정리가 까다로워 미뤄둔 거라면 그 부분도 같이 이야기해 보면 좋겠습니다.

## 4. 새 엔드포인트 리뷰 (이번 회차 핵심)

### 4-1. 구인게시판 CRUD — `/board/write` · `/board/[id]/edit` · `/api/requests/[id]` (BestSeal)

돌봄 요청 글쓰기 화면이 4단계(서비스 선택 → 날짜·장소 → 반려동물 → 상세 내용)로 잘 짜여 있고 디자인 완성도도 높습니다(E2E L11).
무엇보다 쓰기 경로의 보안이 제대로 잡혀 있어 좋았습니다. 쓰기는 Server Action(`actions/requests.ts`)에서 처리합니다.

```ts
const user = await getAuthUser();
if (!user) { /* 인증 필요 응답 */ }       // 생성·수정 모두 로그인 확인
// 수정 시:
if (existing.owner_id !== user.id) { /* 본인 글만 수정 */ }   // 소유권 확인
```

생성·수정 모두 로그인을 확인하고, 수정은 글 작성자 본인인지까지 검사하죠. "조회는 API 라우트, 쓰기는 Server Action"이라는 팀 컨벤션도 일관되게 지켰습니다.
구인글 목록·상세 조회 API(`/api/requests`, `/api/requests/[id]`)도 실데이터로 정상 응답하고요(E2E L10).

- [제안] 쓰기 페이지(`/board/write`·`/board/[id]/edit`)가 비로그인 상태에서도 폼이 그대로 열립니다(E2E L11, 헤더에 로그인 버튼이 뜬 채 4단계 폼 노출).
  제출은 Server Action이 막아주니 데이터가 들어가진 않습니다. 다만 사용자가 폼을 다 채운 뒤 마지막에야 막히는 흐름은 아쉽죠.
  페이지 진입 시 로그인 여부를 확인해 비로그인이면 로그인으로 보내주면, 끝까지 채운 내용을 날릴 일이 없습니다.
- [제안] `/api/requests/[id]` GET이 `createServiceClient`(RLS 우회)로 조회합니다. 공개 게시판이라 동작엔 문제없습니다만,
  "조회를 service client로 우회할지, anon에 SELECT 정책을 열지"는 이전부터 미뤄둔 팀 숙제죠. 이번에 한 번 방향을 정해 두면 좋겠습니다.
- [제안] GET 에러를 `error.message`로 그대로 노출합니다. 이건 다른 조에도 공통으로 드리는 이야기인데, 자체 코드로 매핑하고 원문은 서버 로그로 돌리는 편이 안전합니다.

### 4-2. 펫시터 지도 실데이터 전환 · 장소 검색 (박규나)

지도 데이터를 mock에서 Supabase 실데이터로 옮겼고(2fbdb30), 장소명 검색으로 지도를 이동시키는 기능도 붙었습니다(b9b2351).
지도 영역 자체는 강사 리뷰 포트가 카카오 개발자 콘솔에 등록돼 있지 않아 화면에선 빈 영역으로 보입니다(코드·env 문제가 아니라 도메인 등록 한계입니다).
목록·필터·정렬은 정상 동작합니다(E2E L2).

### 4-3. 유저 프로필 불러오기 (gyuhwa)

`feat: user profile 유저정보 불러오기`(eee830a)로 프로필 데이터 연동이 들어왔습니다. 7차에 칭찬했던 인증 SSOT(UserProvider/userStore) 위에
프로필 정보를 얹는 흐름이라 무리 없이 이어졌습니다.

## 5. 팀 공통 / 협업

- 역할 분담이 또렷합니다. 채팅(영은), 구인게시판 CRUD(BestSeal), 지도·검색(박규나), 인증·프로필(gyuhwa)이 각자 영역을 끌고 가는 모습이네요.
  BestSeal이 이번에 게시판 CRUD를 통째로 맡으면서 분량이 고르게 퍼진 점도 좋았습니다.
- `npx tsc --noEmit`이 0건으로 빌드가 깨끗합니다(7차에 이어 유지). anon 키로 `users`·`requests`·`reservations`·`payments`를 읽어도
  빈 결과가 나와서 RLS도 잘 막혀 있고요.
- 다만 "쓰기 페이지에 로그인 가드가 없다"가 게시판에서도 똑같이 보입니다. 다른 화면에도 같은 패턴이 숨어 있을 수 있으니,
  "로그인이 필요한 페이지는 진입 시 한 번 확인한다"는 규칙을 팀에서 정해 맞추면 좋겠습니다.
