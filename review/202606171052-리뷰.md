## 2. 이번 회차 핵심 — 실시간 채팅 (0sliverchoi321z, 영은)

535줄짜리 `chat/page.tsx`에서 데이터/상태 로직을 훅 3개(`useChatMessages`/`useChatRooms`/`useRequest`)로 떼어낸 방향이 좋습니다. 컴포넌트는 렌더, 훅은 상태를 맡게 한 의도가 분명합니다.

**잘한 점**
- **구독 cleanup이 교과서적입니다.** `useChatMessages.ts:86-88`에서 realtime 채널을 `removeChannel`로 정리하고, 채널명을 `room-${activeRoomId}`로 방별 분리한 뒤 의존성에 `activeRoomId`를 넣어 방을 옮기면 재구독합니다. 필터(`room_id=eq.${activeRoomId}`)까지 정확합니다.
- **전송 경합(더블클릭) 방어가 됩니다.** `chat/page.tsx:78`의 `if (... || sending) return`에 `finally`로 `sending`을 풀고 버튼도 `disabled={sending}`(`:480`)으로 잠급니다. 동시에 눌러 두 번 전송되는 건 막힙니다.

**[필수] 메시지가 화면에 두 번 표시됩니다 — "중복 전송 막기"가 실제 원인을 못 막았습니다**

`handleSend`가 성공하면 `addMessage(result.data)`로 메시지를 한 번 append하는데(`chat/page.tsx:87`), **realtime INSERT 구독이 같은 행을 또 append**합니다(`useChatMessages.ts:73-82`). 두 경로 모두 id 기준 중복 검사 없이 `setMessages((prev) => [...prev, ...])`로 그냥 밀어 넣다 보니, **본인이 보낸 메시지가 두 번 보이는 게 오히려 정상 경로**가 돼버렸습니다.

커밋명은 "중복 전송 막기"지만, `sending` 가드가 막는 건 *네트워크 전송*의 중복이지 *화면 표시*의 중복이 아닙니다. 원인이 다른 곳에 있었던 셈이죠. 해법은 "메시지의 진실 소스를 하나로" 모으는 겁니다(가이드 1번). realtime 한 경로만 신뢰하거나, 양쪽에 id 중복 가드를 넣으면 됩니다.

> E2E로는 직접 확정하지 못했습니다. lookpup은 로그인이 OAuth 전용이라 리뷰에서 2계정 동시 로그인 + Supabase Realtime을 켠 상태를 만들기 어려워, 이 항목은 **코드로 확인**했습니다. 한 가지만 확인 부탁드립니다. messages 테이블에 Realtime(Replication)이 켜져 있나요? 켜져 있으면 현재 코드는 100% 중복이고, 꺼져 있으면 상대 메시지가 아예 안 올 겁니다.

**[제안]** `useChatRooms.ts:77-83`의 `deleteRoom`/`deleteApplicant`가 클라 목록에서만 제거합니다(주석에도 인정해 두셨네요). 새로고침하면 되살아나서 "나가기"가 가짜 동작처럼 보입니다. 서버 삭제 API를 붙이기 전까지는 사용자가 오해할 소지가 있습니다.

## 3. 멤버별 — 응집도·결합도 / React·Next·TS

### Gyu-me (박규나) — 펫시터 지도

**잘한 점 (렌더 최적화가 정확합니다)**
- 지도 객체를 `mapRef.current`로 들고 `initMap`에서 `if (... || mapRef.current) return`(`KakaoMap.tsx:76`)으로 **최초 1회만 생성**하고, 이후엔 `drawMarkers`로 마커만 갈아끼웁니다. 마커가 바뀔 때 지도 전체를 다시 만들지 않는 건 좋은 판단입니다.
- `onMarkerClickRef`로 콜백을 ref에 담아(`:68-72`) 마커 클릭 리스너가 stale closure를 잡지 않게 한 패턴이 인상적입니다.
- E2E에서 펫시터 목록·필터·정렬(거리순 haversine)이 잘 동작합니다(총 9명, 평점·지역·가격 렌더).

**[제안] markers prop의 참조가 불안정합니다 (`petsitters/page.tsx:316` → `KakaoMap.tsx:169-173`)**
부모가 `filtered.map(...)`으로 **매 렌더마다 새 배열**을 만들어 내려보냅니다. 필터·검색·정렬이 그대로여도 부모가 리렌더되면 참조가 달라져 `drawMarkers`가 다시 돕니다. `useMemo`로 markers를 메모이즈하면 불필요한 재그리기가 줄어듭니다. (5차에 짚은 "객체 참조 리렌더"의 연장선입니다.)
**[제안]** `drawMarkers`는 호출될 때마다 마커 전부를 `setMap(null)`로 지우고 다시 만듭니다(`:106-127`). 선택 마커 하나만 바뀌어도 9개를 모두 새로 만드는 구조죠. 지금 규모는 괜찮지만 실데이터로 수백 개가 되면 체감되니, 선택 마커만 `setImage`로 바꾸는 식으로 좁히면 좋습니다.
**[사소]** `window.kakao: any`와 ref들의 `useRef<any>`는 SDK 타입이 없어 어쩔 수 없는 면이 있지만, 최소한의 인터페이스만 선언해 둬도 `any` 누수가 줄어듭니다. Script URL `//dapi…`(`:178`)는 `https://`로 명시하는 걸 권합니다.

### gyuhwa9922 — 로그인 사용자 정보 / 로그아웃·verification

**이번 회차에서 가장 좋은 설계 개선이라 따로 짚습니다.**
- 5차 때 Header가 직접 `getUser`+`fetchUserProfile`을 들고 myprofile과 중복 조회하던 구조를, 이번에 **`UserProvider`(`getUser`+`onAuthStateChange`+cleanup `unsubscribe`)가 한 번만 조회해 zustand `userStore`에 담고, Header는 `useUserStore`로 구독만** 하도록 바꿨습니다(`Header.tsx:35`). 인증 상태를 단일 출처(SSOT)로 끌어올린 모범 변경입니다. 5차에 "공유 훅 통합 여지"로 남긴 지적을 정확히 풀었습니다.
- `userStore`의 `isLoading` 초기값을 `true`로 둔 덕에(`:23`) Header가 `isLoading ? null : ...`(`Header.tsx:100`)로 **초기 깜빡임을 막았습니다.** 5차의 "isLoggedIn 초기 false 깜빡임"도 함께 닫혔습니다. 깔끔합니다.

**[제안] `UserProvider`가 `users` 테이블을 클라이언트에서 직접 SELECT합니다 (`UserProvider.tsx:14-18`).**
본인 행 조회라 RLS에 "본인 행 SELECT 허용" 정책이 있어야 동작합니다. 정책이 없으면 `data`가 null이 되고 `clearUser()`로 빠져, 로그인했는데 비로그인 헤더가 뜹니다. UI 프로바이더가 DB 스키마·RLS에 직접 묶여 있는 구조라, 서버에서 프로필을 내려주거나 API를 경유하면 RLS가 바뀌어도 덜 깨집니다. (확인 부탁: 로그인 세션의 본인 행 SELECT 정책이 켜져 있나요?)
**[제안]** `userStore.verifyUser`(`:26`)가 정의돼 있는데 호출하는 곳이 안 보입니다. verification 흐름에 연결하거나, 의도를 메모로 남겨 죽은 함수로 남지 않게 해주세요.

## 4. 응집도·결합도 핵심 (오늘 주제)

1. **[필수] 채팅 메시지의 단일 소스가 없습니다(영은).** 낙관적 추가(addMessage)와 realtime이 같은 상태를 두 경로로 건드리면서 중복이 생깁니다. "메시지의 진실 소스를 하나로"가 응집의 핵심입니다(2장).

2. **[칭찬→유지] 인증 상태 SSOT화(gyuhwa).** Header가 지던 인증 조회 책임을 `UserProvider`/`userStore`로 끌어올린 건 결합도를 낮춘 모범입니다. 다른 페이지(myprofile 등)도 같은 store를 쓰도록 차차 통합하면 좋겠습니다.

3. **[제안] `chat/page.tsx`가 여전히 535줄입니다.** 훅 분리는 잘 했지만 모바일·데스크톱 레이아웃이 한 파일에 통째로 들어 있어 JSX가 큽니다. `ChatMobileView`/`ChatDesktopView`로 쪼개면 응집도가 올라갑니다. `DUMMY_POSTS` 더미와 실데이터가 한 화면에 섞여 있는 점도 정리 대상입니다.

4. **[제안] 지도 markers prop 참조 불안정(박규나)** — `useMemo`로 결합 완화(3장).

5. **[제안] `UserProvider`의 users 직접 SELECT(gyuhwa)** — UI 프로바이더가 DB·RLS에 직접 묶여 있습니다. 서버/API 경유로 추상화하면 RLS가 바뀌어도 덜 깨집니다.

## 5. React·Next·TypeScript 종합

**잘 쓰고 있는 것**
- realtime 구독의 cleanup과 의존성 관리가 정확합니다(`useChatMessages`).
- zustand store + Provider로 전역 인증 상태를 초기 로딩 플래그까지 깔끔하게 관리합니다.
- 지도에서 ref로 stale closure를 피한 패턴은 React를 제대로 이해한 코드입니다.

**더 볼 부분**
- 같은 상태를 두 경로로 갱신하지 않기(채팅 중복) — 상태 관리의 핵심 원칙입니다.
- 매 렌더 새 배열을 prop으로 내리지 않기(`useMemo`) — 자식의 useEffect 과실행을 막습니다.
- 클라이언트에서 DB를 직접 만지는 결합 줄이기(UserProvider).
