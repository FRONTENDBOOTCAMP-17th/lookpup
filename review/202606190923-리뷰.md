# lookpup 9차 코드 리뷰 (2026-06-19)

월요일(6/22) 사용자·관리자 기능 중간 시연을 앞두고, 8차 리뷰(6/18) 이후 dev에 올라온 변경을 이어서 봤습니다. 이번 범위의 새 기능은 펫시터 등록 이미지 업로드(Cloudinary), 펫시터 상세 소개 탭 리팩터, 위치정보 동의 로직, 채팅 unread count 실시간 갱신과 broadcast 복원입니다. 공개 페이지 위주로 E2E를 먼저 돌리고(로그인은 OAuth 전용이라 로그인 이후 화면은 코드로 확인), 그 결과를 출발점으로 코드를 읽었습니다.

먼저 시연 범위에 대한 사실 하나를 짚고 갑니다. 지금 코드에는 **관리자 전용 라우트나 대시보드가 없습니다**(`role: "admin"` 스키마 값만 있고, `/admin` 같은 페이지·신고/회원/정산 관리 화면은 없습니다). 그래서 월요일 "관리자 흐름"은 현재 보여줄 게 없는 상태입니다. 사용자 흐름(메인 → 펫시터 찾기 → 상세 → 약관/개인정보 → 로그인 → 등록/글쓰기)은 시연이 가능합니다. 관리자 기능을 시연에 포함할 계획이 있는지, 있다면 어디까지 만들 생각인지 알려주시면 그에 맞춰 다음 리뷰를 준비하겠습니다.

## 2. 멤버별 리뷰

### gyuhwa (`@gyuhwa9922`) — 펫시터 등록 이미지 업로드 (Cloudinary)

이번 회차의 핵심 신규 기능입니다. 구조부터 잘 잡았습니다. `getCloudinarySignature`를 `"use server"` 액션(`src/app/actions/upload.ts`)에 두어 `CLOUDINARY_API_SECRET`이 브라우저로 절대 넘어가지 않게 하고, 실제 파일 전송(`uploadToCloudinary`)은 클라이언트에서 서명을 받아 Cloudinary로 직접 올립니다. 비밀은 서버에 두고 큰 파일은 우리 서버를 거치지 않고 바로 올라가게, 역할을 잘 나눠두셨습니다. 이미지와 그 외를 `file.type`으로 갈라 `resource_type`을 정한 점, `res.ok`가 아니면 `data.error?.message`를 꺼내 던지는 처리까지 세심하게 챙기셨네요.

**[필수] 서명 해시 알고리즘이 Cloudinary 기본값과 어긋날 수 있습니다.** `upload.ts:9`에서 서명을 `crypto.createHash("sha256")`로 만드는데, Cloudinary의 서명 업로드는 **계정 설정에서 따로 바꾸지 않으면 SHA-1이 기본**입니다. 계정이 SHA-256으로 설정돼 있지 않으면 업로드 요청이 `Invalid Signature`로 거절됩니다. 지금 실제 업로드가 성공하고 있는지 한 번 확인해 주세요. 계정을 SHA-256으로 맞춰뒀다면 그대로 두되 그 사실을 팀 노트에 남기고, 아니라면 `createHash("sha1")`로 바꾸거나 Cloudinary가 권장하는 `api_sign_request` 방식을 쓰는 게 안전합니다. 시연에서 펫시터 등록을 보여줄 거라면 여기는 꼭 실제 업로드까지 한 번 돌려보고 들어가는 걸 권합니다.

**[제안] 업로드와 검증의 순서가 거꾸로입니다.** `sitter-register/page.tsx:152-196`의 `handleSubmit`은 프로필·자격증·활동사진을 **먼저 전부 Cloudinary에 올린 뒤** `createSitter`를 부릅니다. 그런데 `createSitter`는 `introduction.length`가 20자 미만이면 거절합니다(`actions/sitters.ts:47-58`). 즉 소개를 짧게 쓴 사용자는 이미지 업로드가 다 끝난 다음에야 "소개글은 20자 이상" 에러를 보고, 올라간 이미지는 Cloudinary에 그대로 남습니다(고아 파일). 자기소개 textarea에 최소 길이 검증을 클라이언트에서 먼저 두고(아래 [사소]의 글자 수와도 연결), 통과한 뒤에 업로드를 시작하도록 순서를 바꾸면, 쓸데없이 올라가는 이미지도 없고 사용자도 덜 헷갈립니다.

**[제안] 폼과 서버의 글자 수 기준이 다릅니다.** 자기소개 textarea는 `value.slice(0, 500)`로 500자에서 자르고 카운터도 `/500`인데(`page.tsx:292, 299`), 서버는 1000자까지 허용합니다(`actions/sitters.ts:49-50`). 둘 중 한쪽 기준으로 통일해 주세요. 시연 관점에선 폼이 500이니 사용자에겐 500이 보이는 게 맞는데, 그렇다면 안내·검증도 500 기준으로 정리하는 게 깔끔합니다.

**[사소]** `page.tsx:481-483`에 `{ //지워야할곳 }` 주석이 남아 있습니다. 제출 전에 정리해 주세요. 또 `latitude: 0, longitude: 0, base_price: 0`을 하드코딩으로 넘기는데(`page.tsx:177-179`), 펫시터가 지도에 0,0(서아프리카 앞바다) 좌표로 박히게 됩니다. 위치·가격 입력 단계가 아직 폼에 없어서 임시로 넣은 거라면, 시연 데이터에서는 어떻게 처리할지 한 번 정해두면 좋겠습니다.

## 4. 팀 공통

**서버 액션의 service client 사용은 이번 경우 수용 가능합니다.** `createSitter`/`updateSitter`가 `createServiceClient()`로 RLS를 우회하는데, 이건 `"use server"` 액션이고 맨 앞에서 `getAuthUser()`로 로그인을 확인한 뒤, `users.is_verified` 검사·`sitters` 중복 검사·소유권 검사를 모두 코드로 직접 합니다. 서버에서만 도는 코드라 시크릿이 새지 않고, 권한 검사만 빠뜨리지 않으면 안전합니다. 다만 이런 "코드로 직접 막는" 방식은 한 군데라도 검사를 빼먹으면 바로 구멍이 되니, 새 서버 액션을 추가할 때마다 "이 액션은 누가 부를 수 있나"를 먼저 정하는 습관을 권합니다.

**머지 중 [필수] 수정이 되돌아간 건은 가볍게 보지 마세요.** broadcast 전환은 7차 [필수]였는데 conflict 해결 과정에서 한 번 사라졌습니다. 이번엔 팀이 잡아냈지만, 다음엔 못 잡을 수도 있습니다. 5차·6차에 빌드가 연속으로 깨졌을 때 권했던 것과 같은 처방인데, PR이 머지되기 전에 `tsc`와 핵심 동작을 한 번 거르는 게이트가 있으면 이런 회귀를 자동으로 막아줍니다. 시연 전 마지막 주이니, 적어도 머지 직전에 dev에서 채팅 2인 송수신을 한 번씩 확인하고 들어가는 걸 권합니다.

**시연 범위를 팀이 명확히 정하고 들어가세요.** 관리자 기능이 없는 상태라 월요일은 사용자 흐름 중심이 됩니다. "어디까지 보여주고, 미완성(위치/가격 입력, 회원탈퇴, 관리자)은 어떻게 설명할지"를 미리 합의해두면 시연 중 당황할 일이 줄어듭니다.
