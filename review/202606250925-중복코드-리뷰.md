# lookpup 중복 코드 리뷰 (2026-06-25)

이번엔 **반복·복붙된 코드**를 한 번 훑었습니다. 같이 드린 「리팩토링 가이드」가 원칙이라면, 이 문서는 그걸 lookpup 코드에 대입한 결과입니다. 무조건 다 합치라는 얘기가 아니라, 지금 빼면 이득인 것과 둬도 되는 것을 나눠 정리했습니다.

먼저 칭찬부터. **이 팀은 "추출"을 할 줄 압니다.** Supabase 클라이언트(`client/server/service`), `modalPresets`, `useAuth`, `distance` 유틸 등을 이미 한곳에 잘 모아두셨어요. 문제는 그 좋은 습관이 **서버 액션과 페이지 폼·포매터에는 아직 안 닿았다**는 점입니다. 능력은 이미 있으니, 그 습관을 액션 레이어와 `lib/format.ts`로 넓히기만 하면 됩니다.

---

## 1. [필수] 인증 헬퍼 `getAuthUser`를 액션 파일마다 다시 만들었습니다

같은 네 줄짜리 함수가 **11개 액션 파일에 각각 복붙**돼 있습니다.

- `actions/requests.ts:26`, `sitters.ts:34`, `reservations.ts:101`, `pets.ts:17`, `notifications.ts:6`, `care-records.ts:8`, `chat.ts:7`, `applications.ts:7`, `payments.ts:8`, `reviews.ts:6`, `services.ts:15`

```ts
async function getAuthUser() {
  const supabase = await createClient();
  const { data: { user } } = await supabase.auth.getUser();
  return user;
}
```

11회면 Rule of Three를 한참 넘겼습니다. `src/lib/auth.ts` 하나로 빼고 각 액션은 import 한 줄로 끝내세요. 그리고 이건 단순 추출보다 아래 2번과 묶어서 "인증 + 가드"를 한 번에 처리하는 게 더 좋습니다.

## 2. [필수] 인증/에러 응답 보일러플레이트가 액션 35곳·라우트 10곳에 반복됩니다

`{ error: { code, message } }` 형태가 액션 35회 이상, API 라우트 10회 이상 반복됩니다.

```ts
// 액션
if (!user) return { error: { code: "UNAUTHORIZED", message: "로그인이 필요합니다." } };
// API 라우트
if (authError || !user) {
  return NextResponse.json({ error: { code: "UNAUTHORIZED", message: "로그인이 필요합니다." } }, { status: 401 });
}
```

응답 "모양"을 통일해 두신 건 칭찬할 점입니다(에러 코드 컨벤션이 일관됨). 다만 메시지 문자열이 곳곳에 흩어져 있어 한 글자만 바꿔도 30곳을 손대야 해요. **에러 팩토리 + 인증 래퍼**로 모으세요. 인증 가드는 빠뜨리면 곧 보안 사고라 한 곳에 모아두는 게 안전합니다.

```ts
// src/lib/responses.ts
export const fail = (code: string, message: string) => ({ error: { code, message } });
export const ERR = {
  unauthorized: () => fail("UNAUTHORIZED", "로그인이 필요합니다."),
  forbidden: (m = "권한이 없습니다.") => fail("FORBIDDEN", m),
  notFound:  (m = "찾을 수 없습니다.") => fail("NOT_FOUND", m),
};
export async function withUser<T>(fn: (user: User) => Promise<T>) {
  const user = await getAuthUser();
  if (!user) return ERR.unauthorized();
  return fn(user);
}
```

여기에 더해, "리소스 조회 → 없으면 NOT_FOUND → 내 것 아니면 FORBIDDEN" 3단 콤보가 update/delete마다 12곳+ 복붙돼 있습니다(`requests.ts:145,198`, `pets.ts:114,172`, `services.ts:89,154` 등). 소유권 체크는 빠뜨리면 곧 보안 구멍이라, `assertOwner(db, table, id, userId)` 헬퍼로 모아 "모든 변경 경로가 소유권을 검사한다"를 보장하는 걸 권합니다.

## 3. [필수] 날짜·시간·가격 포매터를 페이지마다 다시 적었습니다

`formatRelativeTime`("방금 전/N시간 전")과 `formatPeriod`("N월 N일 - N월 N일")이 여러 페이지에 글자까지 똑같이 복붙됐습니다.

- `formatRelativeTime`: `board/page.tsx:64`, `myprofile/posts/page.tsx:46`, `notifications/page.tsx:26`
- `formatPeriod`: `board/page.tsx:51`, `myprofile/posts/page.tsx:31`
- 가격 `.toLocaleString()}원`: 17곳+ 인라인(`petsitters/page.tsx:113`, `book/page.tsx:471~876`, `board/[id]/page.tsx:356` 등)

```ts
function formatRelativeTime(dateStr: string) {
  const diffH = Math.floor((Date.now() - new Date(dateStr).getTime()) / 3600000);
  if (diffH < 1) return "방금 전";
  if (diffH < 24) return `${diffH}시간 전`;
  return `${Math.floor(diffH / 24)}일 전`;
}
```

가장 먼저 빼야 할 후보입니다. 포매터는 복붙본이 글자까지 같고, 의존성이 없어 추출 비용이 0에 가깝고, 표기 통일(원/콤마/상대시간)이 사용자에게 바로 보이거든요. `src/lib/format.ts`에 모으세요. `formatPrice`는 17곳을 한 번에 안 바꿔도, 새 코드부터 쓰게만 해도 이득입니다.

## 4. [제안] 카카오 주소검색 + 디바운스 드롭다운 — 훅으로 빼기 딱 좋습니다

"입력 → 300ms 디바운스 → `searchAddressList` → 추천목록" 로직이 4개 페이지에 거의 같게 들어 있습니다(`board/write/page.tsx:191`, `board/[id]/edit/page.tsx:188`, `myprofile/page.tsx:407`, `petsitters/page.tsx:137`).

로직이 자명하고 4곳이라 Rule of Three도 넘겼습니다. UI는 그대로 두고 로직만 `useAddressSearch()`로 뽑으면 됩니다. (이미 `LocationPickerWithMap` 컴포넌트가 있으니, 그쪽으로 흡수할 수 있는지부터 보는 게 순서예요.)

알림 생성 패턴("users에서 full_name 조회 → 기본값 펫시터 → `createNotification`")도 `applications.ts:122`, `chat.ts:117,200`, `care-records.ts:59`에 반복되는데, 이미 있는 `notificationHelpers.ts`에 `notifyWithSender` 하나 추가하면 자연스럽게 흡수됩니다.

## 5. [제안] DB 행 타입이 파일마다 필드가 다른 채로 재선언됐습니다

`Pet` 타입이 `board/write/page.tsx:76`, `board/[id]/page.tsx:38`, `book/page.tsx:54` 등 4곳에 각각 다른 필드로 선언돼 있습니다.

```ts
// 어떤 곳은 type, emoji
type Pet = { id; name; type: string; age; weight; emoji; image_url };
// 다른 곳은 animal_type, breed
type Pet = { id; name; animal_type: string; breed: string | null };
```

필드명이 `type`/`animal_type`로 갈리는 건 위험 신호입니다(어디선가 매핑 실수가 숨어 있을 수 있어요). `database.types.ts`(생성 타입)가 있으니 거기서 `Pick`으로 베이스를 파생하고 화면별 차이만 남기세요.

```ts
import type { Database } from "@/types/database.types";
type PetRow = Database["public"]["Tables"]["pets"]["Row"];
type PetCard = Pick<PetRow, "id" | "name" | "animal_type" | "breed">;
```

## 6. [사소] 지금은 둬도 되는 것 (무조건 빼지 마세요)

- **다중 필드 폼의 `useState` 나열**(`pet-register/page.tsx`에 13개+): 폼마다 필드가 다 달라서 공통 훅으로 묶으면 오히려 부담입니다. 다만 `useState` 13개 나열은 단일 `useState<객체>`로 바꾸면 가독성이 확 삽니다. 실제로 `board/write`는 이미 `setForm(prev => ...)` 객체 패턴을 쓰고 있으니, **그 좋은 패턴을 다른 폼에도 통일**하는 정도면 충분합니다.
- **글자수 제한 textarea + 카운터**(4곳), **프리셋 버튼 토글**(3곳): className이 페이지마다 미묘하게 달라서, 지금 `<CharLimitedTextarea>`로 묶으면 props가 늘어 오히려 복잡해집니다. 디자인이 굳은 뒤에 빼세요.
- **`createServiceClient()` 35곳 호출**: 이건 중복이 아니라 정상적인 사용입니다(정의는 한 곳, 호출은 한 줄). 추출 대상 아님. 다만 service-role 키는 RLS를 우회하므로, 사용자 입력 기반 쿼리가 RLS 보호 없이 나가는 곳이 없는지는 따로 점검이 필요합니다 — 중복 이슈가 아니라 보안 이슈로요.

참고로 `STATUS_MAP`이 `board/[id]/page.tsx:31`과 `reservations.ts:263`에 둘 다 있지만, 게시글 상태(`open/matched`)와 예약 상태(`pending/accepted`)로 **다른 도메인**이라 합치면 안 됩니다. 이름만 헷갈리니 `POST_STATUS_LABEL`/`RESERVATION_STATUS_LABEL`로 구분만 하세요. `lib/supabase.ts`(anon 싱글톤)와 `utils/supabase/client.ts`는 역할이 겹치니 둘 중 하나로 통일하면 깔끔합니다.

## 한 줄 정리

**컴포넌트·모달·유틸은 추출할 줄 알면서, 정작 서버 액션의 인증·에러 보일러플레이트와 날짜·가격 포매터는 페이지마다 복붙으로 흩어진** 과도기 패턴입니다. 우선순위는 ① `getAuthUser`+에러 팩토리+`withUser`(1·2번) → ② `lib/format.ts` 포매터 모으기(3번) → ③ 주소검색 훅·DB 타입 파생(4·5번) 순서를 권합니다. 6번은 두셔도 됩니다.
